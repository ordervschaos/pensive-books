# A/B-ing the DNA agent at the premise rung — design

**Three things up front.**

1. **The ladder you described already exists as code.** `stageSubsteps("premise")` in
   `supabase/functions/_shared/dna-journey.ts:106-119` is literally `interview (vision) → seed (logline) →
   premise (dramatic question)`. Don't define a new ladder — reuse it, and use `stageComplete(nodes).premise`
   as the harness's terminal predicate. That's a *better* halt than the layer-based one I built, because it's
   the same gate the product uses.
2. **The fixture must include a scripted author.** The premise rung *opens with an interview*. In auto mode
   the agent auto-answers itself with the "I'm away" stub — so a naive harness measures the agent's ability
   to **invent** an author, not to **interview** one. That is a different (and much easier) task.
3. **One run per version tells you nothing.** Generation is stochastic. Without repeated trials you are
   comparing two samples of noise. This is the failure mode that kills most hand-rolled model A/Bs.

`eval-logline.mjs` is the template. It already does everything except *multi-turn*: it evaluates one
`dna-expand` call. The agent eval is the same shape wrapped around a loop.

## 2. Define "version" before you run anything

"Two versions of the DNA agent" is a bundle of five knobs:

- system prompt (`prompts.ts` `SYSTEM_THREAD`)
- tool belt (`tools.ts` — e.g. with/without the newly wired `read_*` diagnostics)
- context assembly (`context.ts` — what gets injected, journey objective on/off)
- model / tier / provider
- loop policy (turn ceiling, force-commit threshold, auto-mode rules)

**Change one per experiment.** If A and B differ in prompt *and* model, a result tells you nothing about
either. Write the variable down in the fixture file before running.

## 3. How to actually run two versions

### ✅ Recommended: a variant switch inside the deployed function

Add `context_variant text` to `book_agent_runs` (matches the existing `context_*` column family), have
`threadSystem()` / the tool assembler branch on it, and set it when the harness creates the thread.

Why this and not the obvious alternative: both variants live in **one deployment**, so you can **interleave**
trials — A, B, A, B — and randomize order. Sequential "deploy A, run 20, deploy B, run 20" is
**time-confounded**: provider-side model updates, load, and cache state all drift between the halves, and
you cannot separate that drift from your change.

### ❌ Rejected: a local prompt mirror

Running the loop against a locally-held copy of the prompt is the `eval-bridge` drift trap — already a
standing decision in this repo. The system under test must be the deployed path, exactly as
`eval-logline.mjs` insists ("real prompt bytes, real provider, logged to `ai_calls`").

### ⚠️ Caveat if the model is your variable

`ai_provider` is a **global** admin setting (`model-config.ts:26`). Interleaving requires a per-run
override; otherwise a model A/B is forced back into the sequential (confounded) shape.

## 4. The fixture

```jsonc
{
  "id": "haunted-chatbot",
  "variable": "tool-belt: with vs without read_* diagnostics",   // what this run is testing
  "brief": { /* same shape as eval-logline-tasks.json */ },
  "author": {                    // the SCRIPTED AUTHOR — answers to ask_author
    "default": "…",              // fallback so a run never deadlocks
    "keyed": { "ending": "…", "audience": "…" }   // matched on question topic
  },
  "must_mention": ["chatbot|machine", "grief|dead husband"],  // distinctive element survival
  "must_avoid": ["\\bAI\\b thriller"],
  "reference": { "logline": "…", "dramatic_question": "…" }   // for --refs calibration
}
```

Two scope decisions to make deliberately:

- **`seed` is `manual: true`** in the substep model — the logline is normally *author*-written. Decide
  whether the agent proposes it or the fixture supplies it. This materially changes what you're comparing.
- **`update_vision` writes directly** to `books.brief.vision` (`exec-tools.ts:105`), not through a proposal.
  So the apply loop isn't involved for that substep — but the trajectory still lands in `steps`/`ai_calls`.

## 5. What to measure

Four families. The first three mirror `eval-logline.mjs`; the fourth is the one to add.

### A · Did it get there — deterministic, cheap, run always
- `stageComplete(nodes).premise` reached? (the product's own gate)
- per-substep: interview / seed / premise each `done`?
- required fields present per `dnaSchema`
- `must_mention` / `must_avoid` — did the brief's distinctive element survive into the logline?
- lints firing at this rung
- failure modes: errored, hit `MAX_TURNS`, left proposals unapplied, parked on a question

### B · How it got there — trajectory, the level you currently lack
Turns-to-gate · tool-call histogram · read-round-trips per turn · `ask_author` count · discarded/failed
proposals · retries · cache-read ÷ input · cost · wall-clock.

> **Efficiency at equal quality is the whole point.** A version that reaches the same premise in half the
> turns is strictly better, and no quality rubric will ever show you that.

### C · Is it any good — absolute rubric (model judge)
`read-logline`, `read-premise`, `audit_vision`. Gives partial credit and per-axis diagnosis. Known weakness:
absolute 1–5 scores are noisy and compress toward the middle, so they rarely separate two decent versions.

### D · Which is better — pairwise preference ← **add this**
Show one judge both premises **from the same brief and same fixture**, ask it to pick one and say why.
Pairwise discriminates far better than absolute scoring on creative output, because the judge is doing a
comparison rather than calibrating an internal scale.

Non-negotiable detail: **randomize position** (or run both orders and average). LLM judges have a real
position bias, and an unrandomized pairwise eval will happily report a winner that is just "slot A."

### The distinction worth holding
"What do I measure against?" has two answers, and you need both:
- **against a bar** (A/C: does it reach the gate, does it pass the rubric) — catches regressions
- **against each other** (D) — picks a winner

## 6. The trap: variance

Generation is stochastic; two single runs differ for reasons unrelated to your change.

- Budget **N trials × M fixtures**, per variant. `eval-logline.mjs` already has `--trials` for exactly this
  (it reports pass@1 vs pass^k).
- **Start small and honest:** 3 fixtures × 3 trials = 9 runs per variant is a *smoke signal*, not a verdict.
  Enough to catch "B is broken"; nowhere near enough to call a 10% quality win.
- Binary gate metrics are the noisiest — small differences need a lot of trials. Pairwise needs the fewest
  comparisons for a usable signal, which is another reason to add family D.
- **Steal `--refs`.** Grading the *reference* outputs proves the tasks are solvable and the graders are
  fair before you trust a single result. Cheapest possible insurance against a broken harness.
- Premise-only is cheap (no prose), which is exactly why it's the right rung to build the loop on — you can
  afford the trial counts that make the numbers mean something.

## 7. Build order

1. **Apply half of the driver** — extend `agent-build-dryrun.mts` to apply + `continueAgent`, halting on
   `stageComplete(nodes).premise` instead of the prose layer. (Needs the supabase-client swap.)
2. **Scripted author** — answer `ask_author` from the fixture instead of the `AUTO_ANSWER` stub.
3. **`eval-premise-tasks.json`** — 3 fixtures, with references.
4. **Metrics collector** — the read-only scorer (family A + B) over `ai_calls` + `book_agent_runs`.
5. **`--refs` calibration run** — prove the graders before trusting them.
6. **`context_variant`** column + branch; interleaved A/B.
7. **Pairwise judge** + report: per-variant table, plus win-rate with position randomized.

Steps 1–5 are worth doing even if you never run an A/B — that's the regression harness. Only 6–7 are
A/B-specific.
