# Why today's digest was only book highlights — and what actually adds content

**2026-08-04 · apps/digest**

## The payload first

Today's digest was not thin because of AI settings or a lack of sources. **Production is running
`apps/digest` code from Aug 01 20:33**, because every digest commit since then is unpushed / on the
local `digest-reader-render` branch. In that Aug-01 code there is *no* non-AI fallback: every section
except `readwise` goes straight to the model — and `DEEPSEEK_API_KEY` is not set in the Vercel
production environment. So every feed section throws, gets caught, and is silently dropped. Readwise
survives because it is a template, not a model call.

Your feeds are working fine. Today's 03:00 IST run gathered **10 fresh articles with full bodies**
(Colossal ×3, Marginalian, Tricycle, Lion's Roar…) and shipped **none** of them.

Order of operations, highest delta first:

| # | Action | Effect | Cost |
|---|--------|--------|------|
| 1 | Push/deploy current `apps/digest` | 3 feed sections/day come back (raw-list mode) | $0 |
| 2 | Set `DEEPSEEK_API_KEY` in Vercel prod | unblocks trim / select / write / agent | $0 |
| 3 | `digests.ai_enabled = true` | selection + editorial prose + intro + the reflection section | ~cents/day |
| 4 | Add `ranked` / `search` / `unread` sections | genuinely *new* material from the open web | varies |

Steps 1–2 are bug fixes. Only 3–4 answer your question as asked.

Three independent tells, all pointing the same way:

1. **Bodies stored, sections missing.** `recordPosts` runs *after* the write stage and persists
   everything gathered, used or not. Material present + section absent = the write stage dropped it.
   `buildSection` catches a thrown `writeSection` and returns `{ rendered: null, items }` — "a failed
   section is dropped from the issue, but its posts are still kept."
2. **Zero `ai_calls` rows.** The DeepSeek path throws `DEEPSEEK_API_KEY is not set` *before* the
   try/catch that writes the log row, so a missing key produces a failure with no trace. Current code
   would also have logged a `digest-trim` row per article; there are none, so the trim pass isn't
   deployed either.
3. **`body` is exactly 12000 characters, cut mid-word, with no `` mark.** Current
   `truncateAtBoundary` cuts on a paragraph boundary and appends the private-use sentinel. Exactly-12000
   is the old `slice(0, 12_000)` — i.e. code older than `8d0773e` (Aug 02 16:18).

### Why the deployment is stale

`main` on GitHub ends at `442aade` (Aug 01). Everything after — the paid AI gate, the raw-list
fallback, boundary truncation, the trim pass, the agent rail — sits on `digest-reader-render` locally.

This is **deployment drift**: the artifact serving traffic and the source you are reading have silently
diverged. Everything you verified locally was true — of a program nobody was running.

## Q1 — "will there be more content if we use the AI settings?"

Today: `ai_enabled = false`, `web_search_enabled = false`.

**AI does not add sources. It changes what happens to the ones you have.** Concretely, four gates open:

| Stage | AI off (today) | AI on |
|-------|----------------|-------|
| ②½ **select** (`select.ts`) | `candidates.slice(0, max)` — feed order wins | one cheap call ranks ~16 candidates by substance/fit/variety, picks 4 |
| ③ **write** (`write.ts`) | `renderRawList` — every article dumped whole, 26k–37k chars | 2–6 edited paragraphs, cited, in your voice |
| ⑤ **intro** | skipped | two-sentence "what's in today" |
| `prompt` kind | **dropped entirely** — no fallback exists | "On the practice" actually runs |

So one thing genuinely appears that cannot appear today (the reflection section), and the *quality* of
the cut changes a lot: you are currently reading whatever the feed listed first, at full length.

Note the direction: on a normal day AI makes the digest **shorter and denser**, not longer. If "more
content" means more words, raw-list mode already gives you the maximum. If it means more *worth
reading*, that is the selection pass.

`web_search_enabled` is the separate, narrower gate — the only adapter that pulls the open web, on
Opus with Anthropic's server-side `web_search` tool. It's the one path that bills every run whether or
not it finds anything, which is why it has its own switch inside its own adapter.

**Prerequisite:** `DEEPSEEK_API_KEY` must exist in prod first. Flipping `ai_enabled` today would make
things *worse* — write, select and trim would all throw, and the raw-list fallback is only reached when
the flag is off.

## Q2 — "proactive pull for content across the web — pipeline it"

**The pipeline already exists.** `ADAPTERS` in `adapters.ts` is a registry keyed by section kind; ten
kinds are implemented and six of them pull from outside your subscriptions:

| kind | what it pulls | why it's interesting |
|------|---------------|----------------------|
| `ranked` | HN / reddit / arXiv / GitHub / Lobsters | **borrowed ranking signal** — the world already voted; the score arrives with the item |
| `search` | Anthropic `web_search`, with a hard "discard content farms" prompt | topic beats with no feed |
| `sitewatch` | any page, emits only when the extracted text *changed* | cheapest "watch anything" primitive; reuses the corpus as memory |
| `video` | YouTube channels / podcast RSS → transcript-as-reading | **medium conversion**: an hour of video → six minutes of reading |
| `unread` | your own corpus leftovers (fetched, never used) | free — you already paid to fetch it |
| `inbox` | mail sent to `read+<token>@…` | the only **push** source; curation is free because you subscribed |

Your digest configures: 3 × `feed`, 1 × `readwise`, 1 × `inbox`, 1 × `prompt`. **Zero of the six above
except inbox.** So "pipeline the web" is a *configuration* gap, not a code gap — adding a source is a
row in `digests.sections`, not a new branch in the pipeline. That is the whole point of the
source-adapter shape.

A concrete starter set, once 1–3 are done:

```jsonc
{ "kind": "ranked", "source": "hn",  "query": "philosophy OR attention OR craft",
  "min_score": 150, "max_items": 3, "cadence": "daily" }
{ "kind": "ranked", "source": "lobsters", "max_items": 2 }
{ "kind": "search", "query": "new museum exhibitions and artist profiles worth seeing",
  "max_items": 3, "cadence": "weekly", "weekday": 6 }        // needs web_search_enabled
{ "kind": "video",  "channels": ["@Kurzgesagt", "<podcast rss>"], "days": 7, "cadence": "weekly" }
{ "kind": "unread", "min_age_days": 3, "max_age_days": 30, "cadence": "weekly", "weekday": 0 }
{ "kind": "sitewatch", "urls": ["<a syllabus or a friend's site>"], "cadence": "weekly" }
```

Cadence matters more than it looks: a `weekly` section that fills is better than a `daily` one that
teaches the reader to expect an empty box.

## Two real bugs found on the way

1. **`trimItems` caches into a row that does not exist yet.** It `UPDATE`s `digest_posts SET
   body_clean …` for a `url_hash` that `recordPosts` only inserts at the *end* of the build. For any
   first-seen post the update matches zero rows, so the trim result is never cached and the article is
   re-trimmed (and re-billed) on every future run that touches it. Fix: upsert the row at gather time,
   or move the write into `recordPosts`.
2. **A missing provider key produces an untraceable failure.** In `callDeepSeek`, the
   `DEEPSEEK_API_KEY` check throws before the `try` that writes to `ai_calls`, so the one signal you
   built for exactly this situation stays silent. Fix: validate inside the try, or fail loudly at boot.

Both are **fail-open** behaviours in a place that should fail loudly: a dropped section looks identical
to a quiet morning, and the system is explicitly designed to treat a quiet morning as success
(`skipped`, not `failed`). That design choice is right — but it means a section that *dies* must be
distinguishable from a section that had nothing to say. Today it isn't.
