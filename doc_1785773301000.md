# Would planning fix the eviction loop?

**Answer: yes, but only if "planning" means a durable findings ledger or a harness-owned worklist — not a plan the model writes in prose. And the mechanical backstop stays either way.**

Grounded in the live implementation:
- `supabase/functions/book-agent/transcript.ts:25` — `compactTranscript`
- `supabase/functions/book-agent/transcript.ts:62` — `FORCE_COMMIT_AFTER_READS = 15`
- `supabase/functions/book-agent/advance.ts:428` — the injection site
- `supabase/functions/book-agent/shared.ts:11` — `AgentStep`

---

## 1. The diagnosis under the diagnosis

Both compaction bugs and both fixes share one root cause:

> The transcript is the agent's **only** working memory, and it is also the one buffer the harness is required to prune.

Everything the model learns lives in an evictable cache with no backing store. Consequences:

- **Compaction** is a memory-leak fix that induces **amnesia**.
- **`FORCE_COMMIT_AFTER_READS`** is a deadline that forces action *under* amnesia.

Both are correct given the constraint. Neither gives findings a durable home. That is the hole planning can fill.

### The state-location table

| What | Where it lives | Prunable? | Carries meaning? |
|---|---|---|---|
| Raw read results | transcript `tool_result` | **yes** (>700 chars) | yes |
| `AgentStep` labels | `book_agent_runs.steps` | no | **no** — receipts only |
| Live tree | `<book_state>`, re-injected | n/a (regenerated) | yes, but structural |
| Model's synthesis | *nowhere* | — | — |

The bottom row is the bug.

---

## 2. Why the two compaction bugs generalize

Both are **protection-predicate** bugs — the rule for "what is the working set" was keyed on the wrong signal.

- **v1, count-based window.** A batched turn packs a whole read sweep into ONE message, so a trailing-count of 6 protected the entire 7-message transcript. *Lesson: the unit of protection must match the unit of bulk, and batching decouples message count from token count.*
- **v2, "newest tool message."** The post-apply `✓ Applied` ack is also a `tool_result`, so protection flipped to a ~20-char message right after every apply. *Lesson: a predicate over message **type** breaks when two semantically different things share a type. Predicate over the **property you actually care about** — here, size.*

Current rule (`hasBulkyResults`) is correct because it tests the property directly: `role === "user" && some(block.type === "tool_result" && content.length > STUB_OVER)`.

Two invariants worth naming, both already honored:
- **Replace, never remove** — preserves `tool_use ↔ tool_result` pairing. Removing a `tool_result` is a protocol violation, not just data loss.
- **Determinism** — a retried chain link re-derives the identical transcript, so compaction can't desync a retry.

## 3. Three kinds of planning

### 3a. Plan-as-prose — won't work

Model emits "here's my plan" as an assistant text block. Text blocks aren't pruned (only `tool_result` strings over `STUB_OVER`), so it *survives* — but it's **advisory**. This is the same class as the "batch, don't sweep" prompt guidance already tried, which cut the rate but didn't stop the loop.

Nothing about a prose plan changes the fact that findings are still only in evictable results.

### 3b. Fold-on-read — the recommended fix

**Shape:** every read tool returns two things:
1. the bulk (prunable exactly as today), and
2. a **required distillation** the model writes before moving on, appended to a never-pruned findings ledger.

Then eviction is free: discard the raw scene, keep

```
scene 14 — no controlling metaphor; opens mid-dialogue; POV Mara; value shift flat
```

**The key timing insight:**

> Compaction is lossy **at the wrong moment**. It discards a read *after* attention has moved on, with zero compression. Force the compression at read time — while the content is still in context — and the prune costs nothing the model needed.

**This pattern already exists in the codebase, on a different axis.** `node.authoring.prose_digest` is a per-page prefix fold with an `src_hash`/`prev_hash` chain, which replaced an O(N²) all-pages re-summary. Same move: *fold, don't accumulate*. Continuity does it over prose; the agent loop should do it over reads.

**The slot already exists too.** `AgentStep` is durable and never pruned — but it stores receipts:

```ts
step: { t: "read", label: `Read ${n.kind} “${nodeHandle(n.content)}” in full.` }  // exec-tools.ts:78
```

That tells the model it *looked*, not what it *saw*. Adding a `finding?: string` (model-authored, not harness-authored) turns the step journal into the missing backing store.

**Cost property — this is nearly free.** The ledger should render into `<book_state>` via `withBookState`, not into the stored transcript. That block is already request-time-only and already paid uncached every turn (it deliberately rides *after* the cache breakpoints so the cached prefix stays byte-identical). Appending to it does not break the prefix cache. Contrast: growing the stored transcript invalidates nothing but does re-send forever — which is the original problem.

Sketch:

```
<findings note="what you already learned this run — do NOT re-read these">
  scene 14 · metaphor absent · opens mid-dialogue
  scene 17 · metaphor present but monotone
  scene 22 · clean
</findings>
```

The `[PRUNED …]` stub already says "read again if you need this." With a findings ledger, that line becomes mostly false — which is the point.

### 3c. Worklist-as-harness-state — the strong form, for sweep-shaped tasks

The trigger case was *"a lint with hits scattered across a dozen+ scenes."* The harness **already knows the hit list**. So the agent should never have been free to choose its own sweep:

1. Harness computes the hit list (it does this for the lint anyway).
2. Hands the model **item 1** only.
3. Takes the fix, advances a cursor, hands **item 2**.

This makes the bad state **unreachable** rather than **interrupted**. The gather-forever failure mode requires the freedom to gather; remove the freedom and the mode does not exist.

Also: bounded per-item context means each turn's prompt is small, which directly attacks the ~140s MuleRouter timeout that made the loop crawl at one turn per four attempts.

Cost: it only applies where the harness can enumerate the work. Open-ended asks ("make act 2 better") have no enumerable list.

---

## 4. Where this leaves the mechanical backstop

The stated lesson —

> when a failure mode is a loop, prompt guidance reduces its frequency; only a mechanical stop removes it

— is right. One refinement worth carrying:

> A mechanical **stop** interrupts a loop. A mechanical **state machine** prevents it.

`FORCE_COMMIT_AFTER_READS` is a **watchdog**: it fires at an arbitrary point and commits whatever the model happens to be holding. That's a **liveness** guarantee ("something will happen"), not a **safety** or quality one ("the right thing happens"). Its own injected text admits this — *"even just 2-3"*, *"if truly nothing you've read is fixable yet, call finish."*

Layered, the three mechanisms are complementary, not alternatives:

| Layer | Mechanism | Guarantees |
|---|---|---|
| Prevent | worklist / driven cursor | the loop is unreachable on enumerable work |
| Mitigate | fold-on-read ledger | re-reading is unnecessary; progress is monotone |
| Interrupt | `FORCE_COMMIT_AFTER_READS` | liveness on every other path |

Keep the watchdog. It stops being the *primary* mechanism.

## 5. Recommended order

> **Status 2026-08-03: item 1 SHIPPED and deployed.** What landed: `record_findings` tool
> (`tools.ts`) + handler (`exec-tools.ts`) → a `t:"finding"` `AgentStep` carrying `findings[]`

> guidance in `prompts.ts` (§Working efficiently) + `context.ts` (autonomous_mode). Feed
> rendering in `StepBubble.tsx`. Locked by `transcript.test.ts` (8 tests). Items 2–3 unchanged.

1. **Fold-on-read** — cross-cutting (helps every task shape, not just lint sweeps), small (one optional field on `AgentStep`, one render into `<book_state>`), cache-neutral.
2. **Worklist** — bigger, and only pays on sweep-shaped tasks. Do it after the ledger proves out, and scope it to lint-driven work first.
3. **Watchdog** — unchanged. If the ledger works, `trailingReadRun` should rarely reach 15; that's the metric to watch.

### Success criteria

Measured on a live full-book build (already the §Now-1 priority, with its read-round-trip-per-turn bar):

- **the same node is not read twice in one run** — the direct signal that the ledger replaced re-reading
- `trailingReadRun` reaches `FORCE_COMMIT_AFTER_READS` **zero times** on a normal build
- **no run with >0 reads and 0 applies**
- p50 prompt tokens per turn stops growing with turn index (currently it grows until compaction clamps it)
