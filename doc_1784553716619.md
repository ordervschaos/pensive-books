# Mobile-only `AuthPKCECodeVerifierMissingError` — diagnosis

## Symptom
Google sign-in fails only on mobile (reproduced via Chrome DevTools responsive mode) with:
```
AuthPKCECodeVerifierMissingError: PKCE code verifier not found in storage.
```
`app.pensive.me/auth/callback?code=...` shows the auth error toast; console shows the exchange call throwing.

## Architecture involved
- **PKCE (Proof Key for Code Exchange)**: an OAuth extension where the client generates a random
  `code_verifier`, derives a `code_challenge` from it, sends the challenge up front, and must present
  the original verifier when exchanging the returned `code` for a session. Prevents code interception
  attacks. The verifier has to survive client-side across the whole redirect round-trip (your app →
  Supabase → Google → Supabase → your app), so it's stored in a cookie
  (`sb-<project>-auth-token-code-verifier`).
- **Cookie-based session storage**: `apps/web/src/integrations/supabase/client.ts` uses
  `@supabase/ssr`'s `createBrowserClient`, which persists session + verifier in cookies (not
  localStorage), scoped to `.pensive.me` so both `app.pensive.me` and `pensive.me` can read the same
  session in the future.
- **Circuit breaker**: `panicClearAuthCookies()` (same file, lines 206-282) is a defensive mechanism
  added during an earlier "Invalid Refresh Token: Already Used" incident. On any refresh-token call
  that 400s/401s, it deletes *every* `sb-*` cookie across all plausible `Domain` values, as a
  last-resort cleanup for duplicate-domain cookie corruption.

## Root cause hypothesis
`createBrowserClient` auto-refreshes the session on init if a session cookie is present. On
`/auth/callback`, two independent async flows are in play at once:

1. **Your intended flow**: `handleCallback()` in `Auth.tsx` calls
   `exchangeCodeForSession(code)`, which POSTs `grant_type=authorization_code` and needs the
   verifier cookie.
2. **An unrelated flow**: if the browser is carrying a stale/expired refresh-token cookie (e.g. an
   old mobile session that went stale while the tab sat backgrounded for days — much more common on
   mobile, where tabs persist far longer than on desktop), Supabase's client auto-fires a
   `grant_type=refresh_token` call on page load to try to recover that session.

If (2) 400s *after* the verifier cookie is written but *before* (1) reads it, the panic-clear in (2)'s
failure handler deletes the verifier cookie out from under (1) — a **race condition**: two concurrent
network calls, one's failure handler destroys state the other depends on, and which one wins is
timing-dependent (network latency, device speed), not code-path-dependent. That's why it correlates
with mobile without being caused by the mobile browser engine itself.

## Why DevTools mobile emulation reproduced it
Chrome's responsive/device-toolbar mode doesn't change cookie storage or partitioning — it's the same
Blink engine and cookie jar as plain desktop Chrome. Reproducing it there means the trigger is state
(a stale refresh cookie) or timing, not an engine difference. It's evidence *for* the race-condition
theory, not against it.

## Verification step (before changing code)
Reproduce again, expand the console, and check whether
`[AUTH-DEBUG] panic-clear executed` logs *between* the `fetch /token →` (PKCE exchange request) line
and the `AuthPKCECodeVerifierMissingError` line. If present, confirmed.

## Proposed fix
Scope `panicClearAuthCookies()` to leave `sb-<project>-auth-token-code-verifier` (and its chunk
variants) alone — it's a short-lived, single-purpose PKCE artifact unrelated to the refresh-token
corruption the breaker was built to guard against. Deleting the session/refresh cookies on a refresh
failure is still correct; deleting the verifier is collateral damage.
