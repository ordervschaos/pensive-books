# Why no digest arrived: the scheduler was never scheduled

## The answer first

**No, nothing runs the digest daily.** The endpoint exists and is live, the domain resolves, the
secret is set — but the *trigger* was never created. `apps/digest/SETUP.md:150` says so explicitly:

> The pg_cron `digest-tick` job (README §Scheduling) is **still not scheduled** — unchanged by this
> work, but it's the reason nothing arrives at 6am on its own yet.

And yes — **Supabase pg_cron is exactly the intended mechanism.** It's not a new idea to adopt; the
SQL is already written in `apps/digest/README.md` §Scheduling. It just needs to be run once, by hand,
against the production database. It was deliberately left out of the migrations (reasons below).

---

## Where this sits (the subcontext)

The digest pipeline has four stages. You are missing stage 0.

```
  ┌──────────────────────────────────────────────────────────────────────┐
  │  STAGE 0 — TRIGGER          ← ✗ MISSING. Nothing ticks the clock.    │
  │  pg_cron */15 * * * *                                                 │
  │      └─ net.http_post(digest.pensive.me/api/cron/tick, x-cron-secret) │
  └──────────────────────────────────────────────────────────────────────┘
                                    │
  ┌─────────────────────────────────▼────────────────────────────────────┐
  │  STAGE 1 — SELECT           ✓ built                                   │
  │  due_digests()  → rows whose LOCAL deliver_at passed in last 3 hours  │
  └──────────────────────────────────────────────────────────────────────┘
                                    │
  ┌─────────────────────────────────▼────────────────────────────────────┐
  │  STAGE 2 — CLAIM            ✓ built                                   │
  │  claim_digest_issue()  → the claim IS the lock; one winner per race   │
  └──────────────────────────────────────────────────────────────────────┘
                                    │
  ┌─────────────────────────────────▼────────────────────────────────────┐
  │  STAGE 3 — BUILD + SEND     ✓ built                                   │
  │  buildIssue(issueId)  → sources → dedupe → LLM → Mailgun              │
  └──────────────────────────────────────────────────────────────────────┘
```

Everything below the dotted line has been exercised by hand (the "Run now" button, the smoke
scripts). Only the automatic heartbeat is absent.

## Why it wasn't shipped as a migration

This is the interesting design decision, and it generalises.

A migration is **environment-independent** by contract: the same SQL must be correct on every
database it touches. The scheduling statement violates that twice:

1. It **hardcodes the deployed origin** (`https://digest.pensive.me`). A migration that bakes in a
   production URL is wrong on local and wrong on any preview branch.
2. It **depends on a Vault secret existing first**. Migrations run before you have provisioned
   secrets; a job pointing at a URL that doesn't exist yet would fire, fail, and log an error every
   15 minutes forever — noise that trains you to ignore your own error log.

The term for this split: **schema vs. configuration**. Schema is versioned, replayable, and belongs
in `supabase/migrations/`. Configuration is environment-bound, applied once, and belongs in a runbook.
Putting configuration in a migration is a common and expensive mistake — you end up with migrations
that only work on one machine.

The cost of the split is exactly what happened to you: a manual step in a runbook is a step someone
forgets. Runbooks are checklists, and checklists rot.

## The fix

Run this once in the **Supabase SQL editor** against production. Replace the placeholder with the
same value as the `CRON_SECRET` env var in the `pensive-digest` Vercel project.

```sql
-- 1. Store the shared secret in Vault so the cron body never contains a literal.
select vault.create_secret('<same value as Vercel CRON_SECRET>', 'digest_cron_secret');

-- 2. The heartbeat.
select cron.schedule('digest-tick', '*/15 * * * *', $$
  select net.http_post(
    url     := 'https://digest.pensive.me/api/cron/tick',
    headers := jsonb_build_object(
      'content-type',   'application/json',
      'x-cron-secret',  (select decrypted_secret from vault.decrypted_secrets where name = 'digest_cron_secret')
    ),
    body    := '{}'::jsonb
  );
$$);
```

Then verify:

```sql
select jobid, jobname, schedule, active from cron.job where jobname = 'digest-tick';

-- after ~15 minutes:
select status, return_message, start_time
from cron.job_run_details
where jobid = (select jobid from cron.job where jobname = 'digest-tick')
order by start_time desc limit 5;
```

`net.http_post` is **fire-and-forget** — `cron.job_run_details` will say `succeeded` as long as the
*request was queued*, even if the HTTP call returned a 500. To see what the app actually replied,
read `net._http_response`:

```sql
select id, status_code, content, created
from net._http_response order by created desc limit 5;
```

That distinction — *the scheduler succeeded* vs. *the work succeeded* — is worth internalising. Two
different failure surfaces, two different tables.

### Why `*/15` and not `0 6 * * *`

Because delivery time is **per-subscriber and timezone-local**. `due_digests()` does the local-time
math and returns anything whose local `deliver_at` passed within the last 3 hours. The cron is a
coarse **polling heartbeat**; the *policy* about when a given digest is due lives in SQL, next to the
data. One job serves every timezone. If the cron itself encoded the hour, you would need one job per
timezone — configuration multiplying with users, which is the thing you're trying to avoid.

The 3-hour lookback is the **catch-up window**: it makes a missed tick (deploy, outage) self-healing
rather than a silently skipped day. It is not unbounded, so a week-long outage doesn't produce a
flood of backfilled issues on recovery.

## Why not Vercel Cron?

You could put `crons` in `vercel.json` instead. Two reasons not to, one reason to care:

- **Auth shape mismatch.** Vercel Cron sends `Authorization: Bearer $CRON_SECRET`; the route checks
  the `x-cron-secret` header. You'd have to change the route.
- **Granularity.** Vercel's Hobby plan caps cron at once per day, which cannot serve per-timezone
  delivery. Pro allows minute granularity.
- **One control plane.** The scheduling data (`digests.deliver_at`, `digests.timezone`) already lives
  in Postgres. Driving the tick from Postgres keeps schedule *policy* and schedule *mechanism* in the
  same place, and it's the pattern the repo already uses for publish/revalidate and the
  `revive_stalled_chains` watchdog. Consistency beats novelty here.

## Suggested follow-up: close the runbook hole

The reason you found this by *not receiving an email* is that a missing scheduler is
**silent by construction** — absence of a heartbeat produces no error anywhere. The cheap fix is a
**dead-man's switch**: a query (or a second, much rarer cron) that alerts when the newest row in
`digest_issues` is older than ~26 hours. Monitor the *outcome*, not the *mechanism*; the mechanism can
fail in ways you didn't predict, but "no issue was delivered yesterday" is the thing you actually
care about and it catches every cause at once.

# Addendum — the cron fires, the request dies, and a latent day-losing bug

Scheduled 2026-08-03 (`jobid 3`, `*/15`, active). First tick at 05:30:00 UTC produced one
`net._http_response` row with **`status_code NULL`, `content NULL`**.

Measured against the same endpoint from a laptop at 05:32: `200` in 1.75s cold-ish, 1.00s warm.
**The app is fine.** The request died on the pg_net side, before any reply came back.

The unselected columns hold the answer:

```sql
select id, status_code, timed_out, error_msg, created
from net._http_response order by created desc limit 5;
```

Leading hypothesis: `net.http_post(..., timeout_milliseconds integer default 5000)` — five seconds —
and 05:30 was a cold start on a function that had been idle. Expect `timed_out = true`.

## The bigger problem this exposes

Whatever killed *this* tick, the current design **cannot survive a real delivery morning**, and the
failure would first appear on the one day it matters. Three facts compound:

1. **The tick does the work synchronously.** `route.ts` awaits `Promise.all(rows.map(buildIssue))`
   — source fetches, LLM search/select/write/quiz, Mailgun send — with `maxDuration = 300`. A real
   build is minutes. No `timeout_milliseconds` you'd sanely set on a scheduler tick covers that.
2. **The claim happens first, and it's permanent.** `claim_digest_issue` inserts a row at status
   `queued`; `buildIssue` moves it to `building`. If pg_net hangs up and Vercel aborts the handler on
   client disconnect, the row is stranded mid-status.
3. **`due_digests` excludes a date that has *any* issue row, at any status.**

```sql
AND NOT EXISTS (
  SELECT 1 FROM public.digest_issues i
  WHERE i.digest_id = d.id AND i.issue_date = (p_now AT TIME ZONE d.timezone)::date
)
```

So: one interrupted build → a `building` row that nothing ever revisits → **that day is silently
lost forever.** The next tick sees the date as handled. Retries can't help, because the very
mechanism that makes the claim safe against *duplicates* also makes it unforgiving of *crashes*.

This is the classic cost of **claim-as-lock without a lease**. The claim is atomic (good — no two
workers build the same morning) but it never expires (bad — a dead worker holds it forever). The DNA
side of this repo already learned this: `revive_stalled_chains` is a pg_cron watchdog that re-invokes
any run with no progress for 5 minutes. The digest pipeline has no equivalent.

Note the asymmetry in how it fails: a *duplicate* issue is loud and embarrassing (two emails), so it
got designed against. A *missing* issue is silent. The system is hardened against the failure you'd
notice and open to the one you wouldn't — which is also, exactly, why the cron was missing for two
days before anyone asked.

## Three fixes, cheapest first

**(a) Raise the timeout — one line, buys today.**

```sql
select cron.schedule('digest-tick', '*/15 * * * *', $job$
  select net.http_post(
    url     := 'https://digest.pensive.me/api/cron/tick',
    headers := jsonb_build_object(
      'content-type',  'application/json',
      'x-cron-secret', (select decrypted_secret from vault.decrypted_secrets where name = 'digest_cron_secret')
    ),
    body                 := '{}'::jsonb,
    timeout_milliseconds := 300000     -- match the route's maxDuration
  );
$job$);
```

Honest about what this is: it makes the scheduler hold a connection open for the entire build. It
removes the timeout, not the coupling.

**(b) A lease watchdog — the missing safety net.** Reset any issue stuck in `queued`/`building`
past a threshold so the date becomes claimable again. Mirrors `revive_stalled_chains`. Turns a lost
day into a late day.

```sql
update digest_issues
set status = 'failed', error = 'stalled: no progress for 20 minutes'
where status in ('queued','building') and started_at < now() - interval '20 minutes';
```

(Then `due_digests` needs to stop excluding `failed`/`skipped` rows, or the watchdog must delete
rather than mark — a deliberate choice, since re-running also re-sends.)

**(c) Decouple the tick from the build — the real fix.** The tick should claim and return in
milliseconds; the build should run on its own. That's the pattern the DNA pipeline already uses
(`waitUntil` + self-chain + watchdog). Then the scheduler's timeout is irrelevant by construction,
because the scheduler is no longer waiting on the work.

**Recommendation:** (a) now so tomorrow works, then (b) — a watchdog is worth more than a clean
architecture here, because it converts every unknown future failure into a retry instead of a
silence. (c) when the build gets long enough to need it.

## Dead-man's switch, restated

The earlier proposal is now clearly the highest-value item, not a nice-to-have: alert when the newest
`digest_issues` row with `status = 'sent'` is older than ~26 hours. Every failure mode above —
missing cron, timed-out request, stranded claim — collapses into that one observable. Monitor the
outcome; the mechanism will keep finding new ways to fail.

# Addendum 2 — (b) shipped: the lease, verified in production

`supabase/migrations/20260803180000_digest_stalled_watchdog.sql`, pushed and exercised live.

## Why it takes three changes, not one

The instinct is "add a watchdog." A watchdog alone does nothing here, because the retry path is
blocked at two more points. All three must move together:

| # | Change | Without it |
|---|---|---|
| 1 | `expire_stalled_digest_issues()` marks a stalled claim `failed` | The lease never expires; the row sits in `building` forever |
| 2 | `due_digests()` stops counting a *retryable* failure as "handled" | The scheduler never offers the date again |
| 3 | `claim_digest_issue()` returns the existing row for a retryable failure | The scheduler offers it, the claim returns NULL, nothing happens — an infinite polite loop |

Each is inert alone. That's the shape of most liveness bugs: the fix isn't a component, it's a
*path*, and every gate along it has to open.

## What is deliberately NOT revived

`sending`. It is set immediately before the Mailgun call and `sent` immediately after, so a row stuck
there is genuinely ambiguous — the mail may already have gone. Reviving it risks a double delivery,
the one failure this pipeline was explicitly built to prevent. A stuck `sending` is left for a human.
**Better a missed morning than two of them.** This is a real tradeoff, not an oversight: the
automation deliberately stops where its information runs out.

Retries are bounded twice: `attempts < 3` (incremented by `buildIssue`, never reset by a reclaim, so
the cap is a ceiling and not a treadmill) and the pre-existing 3-hour delivery window. Hitting the
cap leaves a `failed` row with an `error` string — a bounded, legible dead end rather than a silent
stall. Manual "Run now" is unaffected; it doesn't go through `claim_digest_issue`.

`FOR UPDATE SKIP LOCKED` on the reclaim preserves the original guarantee: two ticks racing on a
*retry* behave exactly like two ticks racing on a *first* claim — one winner, one NULL.

## Verified against the live database

Using a fake `issue_date` of 2020-01-01 so no real day was touched (row deleted afterwards; issues
6 and 15 confirmed untouched):

```
1. first claim                                    → 19
2. immediate re-claim (expect null)               → null      ← claim-as-lock still holds
3. strand it at 'building' with an old started_at
4. expire_stalled_digest_issues()                 → 1         ← the lease expires
5. reclaim after expiry (expect the same id)      → 19        ← the day is recoverable
6. set attempts=3
7. claim at cap (expect null)                     → null      ← retries are bounded

due_digests, with p_now inside the delivery window for that date:
A. failed, attempts=3 (cap reached)               → []        ← blocked
B. failed, attempts=1 (retryable)                 → [1 row]   ← offered again
C. sent      (terminal decision)                  → []        ← never re-sent
D. sending   (ambiguous)                          → []        ← never auto-revived
```

B is the test that matters. Before this migration it returned `[]`, and that empty result was the
lost day.

# Addendum 3 — closed: the whole path ran, unattended

## The diagnosis, confirmed

```
id 22  05:30  status_code NULL  error_msg "Timeout was reached"
id 23  05:45  status_code NULL  error_msg "Timeout was reached"
id 24  06:00  status_code 200   error_msg NULL              ← after timeout_milliseconds := 300000
```

`net.http_post`'s default `timeout_milliseconds` is **5000**. A cold Vercel function needs ~1.75s
warm and more when idle, so the tick was losing a coin-flip every 15 minutes. The hypothesis was
right and fix (a) is verified by the very next tick.

Worth noticing *how* it was wrong: the app was healthy the whole time, and `cron.job_run_details`
would have said `succeeded`. The truth lived in a column nobody selected. When a fire-and-forget
mechanism fails, the evidence is never where the mechanism reports.

## The delivery, end to end

To dispatch today's issue immediately: `cron.alter_job(schedule => '* * * * *')` and
`deliver_at := '11:30'` (already past), making `due_digests()` return today at once.

```
issue 23 · attempts 1 · item_count 3 · status sent · delivered_at 06:05:11Z
```

Claimed, built and accepted by Mailgun within ~30 seconds of the tick, first attempt. `delivered_at`
is set **only** after a 2xx from Mailgun, so this is real delivery, not an optimistic write.

Then restored: `*/15 * * * *`, `deliver_at := '03:00'` Asia/Kolkata, and `due_digests()` → 0 rows,
so there is no double-send. 03:00 IST = 21:30 UTC; the first tick that will act on it is 21:30 UTC.

## What the original question actually turned up

"I didn't get today's issue" was, strictly, not yet true — delivery was set to 12:25 IST and the
question came at 11:10 IST. But the instinct was right, and pulling the thread found three real
defects stacked behind it:

1. **No scheduler at all.** The one-time runbook step was never run.
2. **A 5-second timeout on a job that calls a cold serverless function.** Would have failed
   intermittently forever, while reporting success.
3. **Claim-as-lock without a lease.** The first interrupted build would have silently eaten a day,
   permanently, with no retry and no error anywhere.

Only #1 was visible. #2 and #3 are the kind that surface as "it worked for weeks and then one
morning it just didn't." Both are now closed — #2 by a timeout, #3 by a lease and a watchdog.

## Still open

- **The dead-man's switch.** Nothing yet alerts on the *absence* of a delivery. Every failure mode
  above collapses into one observable: newest `digest_issues` row with `status = 'sent'` older than
  ~26 hours. This is the highest-value remaining item precisely because the next failure will be one
  none of us predicted.
- **A stuck `sending` row still needs a human** — deliberate, since reviving it could double-send.
- **The tick still does the work synchronously** (fix (c), deferred). The 300s pg_net timeout and the
  300s `maxDuration` are now the same number, which is tidy but not a guarantee. A build that
  genuinely needs longer will be cut off — and *that* is now survivable rather than fatal, because
  the lease will hand the day back within 20 minutes.
