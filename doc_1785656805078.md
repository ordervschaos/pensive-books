# Issue 15 — design review (reader view) + a delete-only trim pass

**Verdict up front:** the page is not a *digest*, it's a **concatenation**. 55,127 characters of markdown across
4 sections → **22,619 px tall, ~24 screens** of continuous scroll, with **no map, no landmarks, and no exit**.
Every symptom you noticed (no TOC, sections don't announce themselves, cookie-banner text in the body) is a
consequence of one root cause plus three renderer bugs.

Evidence: reproduced the exact stored `content` for issue 15 through the app's own `markdownToHtml` +
`IssueContentView` markup and the app's real type scale.

---

## 0. Where this sits (the pipeline)

```
gather ──► filter ──► WRITE ──► verify ──► assemble ──► RENDER ──► deliver
   │                    │                                  │
   │                    └── ai_enabled:false ⇒              └── markdownToHtml
   │                        renderRawList()                     + IssueContentView
   └── fetch.ts: body.slice(0, 12_000)   ← silent mid-word cut
```

`digests.id=1` has **`ai_enabled: false`**. So `writeSection()` never calls a model — it falls through to
`renderRawList()`, which emits *the entire extracted article body verbatim*, one after another, joined by
`\n\n---\n\n`.

That is the root cause. **The "digest" you are reading is the raw corpus with a header stapled on.**
Everything below is either a consequence of that, or a rendering bug that only becomes visible in that mode.

---

## 1. Root cause: the non-AI path has no editorial layer

| section | markdown chars | items |
|---|---|---|
| Stoicism, habits & ideas | 21,783 | 4 |
| Art worth looking at | 10,061 | 3 |
| Meditation & practice | 22,460 | 3 |
| Untitled section | 823 | 3 |

A 22k-character "section" is a book chapter, not a digest section. `renderRawList`'s comment is honest about
this — *"No synthesis, no transitions — exactly the material the writer itself would have been handed, just
not written."* — but as a **reader-facing default** it's a graceful-degradation path that degrades all the way
to "no product."

Two independent decisions are tangled here, and they should be untangled:

- **Do we *rewrite* the source?** (authorship — needs a model, needs `ai_enabled`)
- **Do we *trim* the source?** (hygiene — subtractive, can't fabricate)

Right now `ai_enabled:false` switches off both. Trimming should not be gated on the authorship toggle. See §5.

## 2. Renderer bugs (visible in the screenshots)

### 2a. The headline is 12px grey; the source is 16px black — inverted

`render.ts:35` wraps **every** markdown link in `<small class="src">`:

```ts
.replace(/\[([^\]]+)\]\((https?:\/\/[^\s)]+)\)/g, '<small class="src"><a href="$2">$1</a></small>')
```

That rule is correct for the AI path, where a link genuinely *is* an inline citation. But `renderRawList`
emits the article head as `**[What Does It Mean To Be Wealthy?](url)** — Daily Stoic`, so the **title** gets
the citation treatment (0.75em, #666) while the **publication name** — which is *not* a link — renders at full
body size. The visual hierarchy is exactly backwards.

**Fix (two halves, both cheap):**
1. `renderRawList` should emit a real heading: `### [Title](url)` + a separate source line.
2. `inline()` should only apply the `<small class="src">` treatment to links that are *inside* a sentence —
   i.e. skip it when the link is the entire content of a heading. Simplest form: run the citation rule on
   paragraph/list lines only, not on heading text.

### 2b. `---` renders as the literal text "---"

`markdownToHtml` has no `<hr>` rule. So `renderRawList`'s article separator (`\n\n---\n\n`) falls through to
the last `else` and becomes `<p>---</p>`. There are **7** of these in this issue. One-line fix:

```ts
if (/^(-{3,}|\*{3,}|_{3,})$/.test(line)) { out.push("<hr/>"); continue; }
```

(Guard it *before* the bullet-list branch, and note `^[-*]\s+` already doesn't match `---` because it
requires whitespace, so ordering is safe.)

### 2c. Silent mid-word truncation

`fetch.ts:83` — `text.slice(0, 12_000)`. In the screenshot: *"…never to prostitute my press to the purposes of
cor"*. In the AI path the model reads past it and nobody notices; in the raw path the reader eats it.

**Fix:** cut at the last paragraph boundary before the cap, and append an explicit
`[Read the rest at Daily Stoic →](url)`. Truncation that admits itself is a feature; truncation that
pretends is a bug.

## 3. Information architecture: there is no map

**No table of contents.** 24 screens with 4 `<h2>`s at y = 247 / 8,108 / 11,866 / 22,201. Between y=247 and
y=8,108 there is *nothing* telling the reader where they are or how much is left.

Design the TOC from **the data model, not the rendered markdown.** `RenderedSection.items[]` already carries
`{title, url, source, image_url}` for every item that went in. So:

```
┌─ Contents ──────────────────────────────┐   ← sticky on desktop, collapsible on mobile
│ Stoicism, habits & ideas          4 · 9m│
│   What Does It Mean To Be Wealthy?      │
│   Stoicism Today is moving to Substack  │
│   …                                     │
│ Art worth looking at              3 · 4m│
│ Meditation & practice             3 · 9m│
│ Highlights                        3 · 1m│
└─────────────────────────────────────────┘
```

Two levels, derived: sections from `content.sections`, entries from `section.items`. The **anchor** for each
entry has to be emitted by the writer (`renderRawList` knows exactly where each article starts — it should
emit `<h3 id="item-N">`). Do **not** post-parse the HTML to find headings; that couples the outline to the
render and breaks the moment AI mode is on.

**Caveat worth stating now:** in AI mode a section is *woven prose* with no per-article structure, so the
second TOC level degrades to "sources used" rather than "jump to". That's fine — but it means the TOC is a
**projection of the section's items**, and its interaction (jump vs. reference) depends on the section kind.
Decide that explicitly rather than discovering it later.

Also missing: reading time, item counts, a back-to-top affordance, and any progress indicator.

## 4. Typography: the scale is too flat to carry 24 screens

| element | size | ratio to body |
|---|---|---|
| `h1` (date) | 1.5rem | 1.5× |
| `h2` (section) | 1.25rem | 1.25× |
| body | 1rem | 1× |
| article title | **0.75em grey** | 0.75× (bug, §2a) |

A 1.25× section heading with `space-y-8` (2rem) above it is *not* a boundary — at reading speed it reads as a
slightly bold paragraph. Over 24 screens the reader loses the plot completely.

What a section boundary should carry (pick 2–3, not all):

- a full-bleed **rule** above it (`border-t`), not just whitespace
- a **mono eyebrow** with the section kind + item count (`FEED · 4 ITEMS`) — you already use mono/muted as the
  metadata voice in `Breadcrumbs` and the item list, so this is consistent, not new
- a **sticky mini-header** that pins the current section title while scrolling — the single highest-value
  addition for a 24-screen page
- much more vertical air *before* than *after* the heading (proximity: the heading belongs to what follows)

Article boundaries inside a section want a **dinkus** or a hairline rule, not `<p>---</p>`.

Also: `line-height: 1.5` at ~66ch on a serif face is tight for long-form. 1.6–1.7 for the prose body.

## 5. The delete-only trim pass — yes, and here's the shape

Crude regex sweep over this issue: **~4,400 chars (8%) of obvious boilerplate**, and that undercounts —
whole *contiguous tails* are junk (the `f_art` cookie-consent block runs ~3,000 chars unbroken), and one
entire "article" (`Stoicism Today is moving to Substack`, ~2,500 chars) is a mailing-list admin notice, not
content. The same regex also produced a false positive (a Carl Jung paragraph), which is the whole argument
for a model doing the residue: **the rule catches the shapes you enumerated; the model catches the shapes you
didn't.**

### The architectural move: make deletion *verifiable*

Do **not** ask a cheap model to "return the cleaned article." That is a rewrite with a promise attached, and
you cannot tell a deletion from a paraphrase after the fact. Instead:

> **The model returns indices, not text.** Code does the deleting.

```
raw body ──► split into blocks (blank-line separated), number them
         ──► model sees: [0] …first 200 chars…  [1] …  [2] …
         ──► model returns: { "drop": [0,1,14,15,16,17], "content_ends_at": 13 }
         ──► code applies the drop list and rejoins
```

Properties this buys you, all of which the "return the cleaned text" version loses:

- **Fabrication is structurally impossible.** The output alphabet is integers. The result is provably a
  subsequence of the input.
- **Output tokens ≈ 30–60 per article**, regardless of a 12k-char input. This is what makes it cheap — you
  are paying for input tokens only, and input is the cheap side of every price sheet.
- **Auditable.** Store the drop list. When it eats a real paragraph you can see exactly which block and why.
- **Reversible.** The raw body stays in `digest_posts.body`; the trim is a derived artifact.

Give it a small tag vocabulary so the drop list is self-explaining and you can tune per-category later:
`nav | cookie_consent | ad | share_widget | subscribe_cta | comments | related | legal | admin_notice`.

### Where it goes in the pipeline

Right after extraction, **before** the body is cached — but versioned:

```
fetch.ts extract() ──► stripReaderPreamble() ──► [NEW] trimBoilerplate() ──► digest_posts.body_clean
                                                                             digest_posts.trim_version
```

Two reasons for `trim_version` (an int) rather than overwriting `body`:

1. `loadCorpus()` already re-cleans on read precisely because *"rows stored before the extractor learned to
   strip r.jina.ai's metadata still carry it verbatim… every future run reuses it instead of re-fetching a
   clean copy."* The same trap applies here: a cached bad trim outlives the fix. A version int lets you
   re-trim on read when the trimmer improves, without re-fetching.
2. You pay the model **once per URL, ever**. On a re-run the cache makes it free.

### Deterministic pre-pass first

Extend `cleanBody()` with a boilerplate blocklist before you spend a token — `Manage Consent Preferences`,
`Switch Label label`, `checkbox label label`, `Advertisement`, `Share this:`, `Comments are closed`,
`Consent Leg.Interest`. That's most of the `f_art` tail for zero cost and zero latency. The model then handles
the long tail — and, importantly, the *semantic* cases a blocklist can never catch, like "this whole article
is a newsletter migration announcement."

### The one product decision to make

This digest has **`ai_enabled: false`**. A trim pass is still an LLM call. Either:

- **(a)** trimming is exempt from `ai_enabled` — defensible, because a delete-only pass performs no
  authorship and cannot put words in anyone's mouth; the `ai_enabled` flag is about *voice*, not *hygiene*; or
- **(b)** it gets its own toggle (`clean_enabled`), which is honest but is a third switch the reader has to
  understand.

**Recommendation: (a)**, and say so in the settings copy — "we always strip cookie banners and ads; AI writing
is separate." The verifiable-subsequence property in §5 is what earns that exemption.

**Model:** DeepSeek is already wired (`DEEPSEEK_API_KEY`, `ai_provider` switch). At ~30–60 output tokens per
article this is rounding error even at a 6-section daily cadence.

## 6. Smaller things

- **"Untitled section"** — the `readwise` section (`smsahmxsy`) has a literal title of `"Untitled section"` in
  `digests.sections`. Data bug, not a render bug. It needs a per-kind fallback (`Highlights`) *and* the editor
  shouldn't let a section be saved untitled.
- **No intro.** `writeIntro()` returns `""` when `ai_enabled` is false (`write.ts:175`), so the page opens
  cold into a 22k-character wall. A non-AI intro is trivially derivable and needs no model:
  *"4 sections · 13 items · about 25 minutes."*
- **Duplicate headlines.** In raw-list mode the mono source list at the foot of each section repeats titles
  already used as article heads inside it. Either suppress the list in that mode or relabel it "Sources".
- **`ANY_IMAGE` swallow.** `imageTag` silently drops URL-bearing images (`render.ts:61`). Correct for the AI
  path (anti-fabrication). But `renderRawList` passes real extracted articles whose images are *real* — a
  design section that is all-text because every legitimate image was dropped as a safety measure is worth
  knowing about.

## 9. The bigger bug underneath: `cleanBody` was deleting text and demolishing structure

Reported from the reader's side: sub-heads, pull-quotes and paragraphs all landing as identical undistinguished
paragraphs, and passages simply **missing** against the original article. Both traced to `entities.ts`, and
they are two separate faults that had been hiding each other.

### 9a. `isLinkHeavy` was deleting real paragraphs

```ts
const links = block.match(/https?:\/\//g)?.length ?? 0;
return links > 0 && block.length / links < 300;      // ← "chars per link under 300 ⇒ nav row"
```

Characters-per-link is the wrong axis. **A 200-character paragraph containing one inline citation scores 200
and was deleted.** In the Daily Stoic perseverance piece that removed, among others:

> As mentioned before, hardship allows you to show your true character. So, embrace hardship. *Amor Fati*.
> Love your fate. Embrace every single moment, even moments of hell.

— gone for no reason other than that "Amor Fati" was a link. It also ate the article's own section headings,
because this extractor writes them as `## [](url)How do we persevere?` — an **empty-label permalink anchor**,
which renders nothing but counted as a full link.

The distinguishing property is not how *often* links appear but **how much of the block is anything else**. A
nav row is links plus separators; a paragraph is the author's own sentences with a link inside one of them.
So: strip empty-label anchors first (they present nothing to the reader), then measure the visible text that
is *not* link label — both as a share of the block and in absolute terms.

**Measured over all 43 stored bodies: 109 blocks restored,** overwhelmingly real prose. On issue 15 alone
that is **+8,591 characters of article text** that had been silently deleted before anyone could read it.

### 9b. `cleanBody` returned flat text, so all markup died

`stripMarkdownSyntax` removes `#`, `>`, `*`, `_` — and its output *was* the return value. Defensible when
this fed a one-paragraph teaser; wrong the moment `renderRawList` began emitting whole articles.

The fix is a one-line change with a clean principle behind it: **judge on the stripped text, return the
original block.** Judging and rendering want opposite things — the chrome and length decisions are easier on
flat text, and the reader wants the structure. `markdownToHtml` could already render every construct
involved; it simply never got the chance.

### 9c. What that uncovered (each fixed)

Restoring structure made three latent bugs visible for the first time:

- **Heading collision.** Article titles are `##`; source bodies carry their own levels — and a fixed `+1`
  fails because one site opens at `#` and another at `##`. `demoteHeadings` re-bases so the *shallowest*
  heading in a body lands at `###`, preserving relative depth inside the article.
- **`#{4,6}` rendered as literal hashes.** `markdownToHtml` matched only `#{1,3}`, so `##### Performance
  Cookies` printed its hashes. Now `#{1,6}`, clamped at `<h6>`.
- **Underscore litter.** Real markdown nests emphasis (`**_[title](url)_**`), so by the time the underscore
  rule ran, the character before the opening `_` was the `>` of a `<strong>` — the pair never matched and
  both markers survived onto the page. `>`/`<` now count as boundaries, `__strong__` is supported, and the
  closing side accepts any non-word character (a curly apostrophe in `_Exposure Therapy_’s` was the last
  survivor). The opening side stays a narrow whitelist, which is what keeps `used_at` intact.
- More furniture surfaced as headings once headings existed (`Tags`, `Like this:`, `Newswire`,
  `Discover more from …`, `Your Privacy Choices`) — added to the blocklist.

### Verified

Issue 15 rebuilt from raw bodies: **`<h3>` 13 = exactly the 13 articles** (no collisions), `<h4>` sub-heads,
12 blockquotes, 42 italics, 17 bolds, 9 rules, **0 stray underscores** (was: litter in every nested-emphasis
paragraph). 10 renderer assertions pass including `used_at` protection and the curly apostrophe. `tsc` +
`next build` green.

### The lesson worth keeping

Both faults were **invisible by construction**. `cleanBody` flattened markers, so unmatched emphasis left no
trace; it returned only what it kept, so deleted paragraphs left no gap. A filter that logs nothing and a
renderer that swallows what it can't parse compound into a pipeline that quietly ships 1/6 less article than
it fetched. This is the same argument as §5's index-returning trim pass: **make deletion legible.** Had
`cleanBody` recorded what it dropped, this would have been a one-look diagnosis instead of a reader noticing
a missing sentence.

## 10. Link size and paragraph rhythm — one shared stylesheet, two holes in it

Two reader-side reports, both traced to `issueStyles` doing less than the code around it assumed.

### 10a. Inline links were shrunk to 0.75em mid-sentence

`.src` was applied to **every** markdown link in prose, so a verbatim article's own sentence link —
*"…the kind of lessons we write about in `our daily email newsletter`. Every morning…"* — rendered at
two-thirds size. It reads as a rendering fault because it is one.

The instinct is to stop shrinking `.src`. That is wrong: it would also flatten the AI path's real citations
(the reader asked for "source in small words") **and** blow up the article byline, which genuinely is
metadata. The two cases want opposite things, so the renderer has to be told which it is:

- `RenderOpts.citations` — true for AI-written sections (a link is a source appended to a clause), false for
  a verbatim article body (a link belongs to the sentence).
- `isVerbatimSection(markdown)` — **inferred, not stored.** `renderRawList` always opens with `## [Title](url)`
  and the writing constitution forbids the model from emitting headings at all, so a leading `## [` is an
  unambiguous signature. Inferring costs no schema change and is correct for issues **already in the
  database**, which a new column could never be.

Body links now render at full size in ink with a hairline underline; `.src` keeps its 0.75em and once again
means exactly one thing.

The byline needed a home after that, since it can no longer ride on `.src`. It is identified
**structurally**: `h3 + p`. That is only safe because two invariants hold — `demoteHeadings` guarantees an
article's own sub-heads start at `h4`, so an `h3` is only ever an article title; and `renderRawList` now
**always** emits a byline, falling back to the bare domain. Without that second change, an article whose feed
declared no source would have handed byline styling to its first real paragraph.

### 10b. Paragraphs ran together with no gap

`issueStyles` never set `p` margins. Three renderers consume it and two were compensating by accident — the
reader page via a Tailwind `space-y-3` utility on its wrapper, the mailed HTML via browser defaults (no
Tailwind reset in a standalone document). The **preview page had neither**, and Tailwind's preflight zeroes
`p` margins, so every paragraph ran into the next.

Paragraph, list and item spacing now live in `issueStyles`, and the reader page's `space-y-3` is gone so
there is one owner. This is the same failure as §8's `globals.css` discovery, one layer down: *a shared
stylesheet that is missing a rule looks fine wherever something else happens to supply it.*

### Verified

Computed styles on the rebuilt issue: body paragraph `margin-top: 14.4px` (was 0 in preview), inline link
`16px / #1a1917 / underline #bbb` (was `12px / #666`), byline `12.8px / #666`. 4 assertions on the
citation split and `isVerbatimSection` in both directions. `tsc` + `next build` green.

## 11. Section chrome and the table of contents (items 4–5)

### What shipped

- **`<Contents>`** — a `<details open>` block above the issue: total items and minutes, then one row per
  section (title · N items · M min), and under each **verbatim** section its articles as jump links.
- **Sticky section headers** — each section's `h2` pins to the top of the viewport while that section is on
  screen, with its item/minute count on the right.
- **Rules between sections**, so a boundary is a boundary and not just whitespace.
- **Anchors**: `RenderOpts.anchorPrefix` gives every article `h3` an `id="{sectionId}-{n}"`.

**No JavaScript.** `<details>` collapses natively and `position: sticky` pins natively, so both survive in a
Server Component with no bundle shipped. An IntersectionObserver would have bought nothing here.

### The design decision worth keeping

The outline is computed from **`content.sections[].items`** — the data — and the anchor for item *n* is
`itemAnchor(sectionId, n)`, the same string the renderer stamps onto the *n*th `h3`. Nothing parses the
rendered HTML looking for headings.

That works because of an invariant established earlier in this document, not by luck: `renderRawList` emits
exactly one `h3` per item in item order, and `demoteHeadings` (§9c) guarantees an article's own sub-heads
start at `h4`. So **the Nth `h3` IS `items[N-1]`**, positionally, and the TOC can address it without ever
looking at the render. Had the anchors been slugs of heading text instead, two articles with the same title —
or a title containing punctuation — would have silently collided.

Only verbatim sections get the second level. An AI-written section weaves its sources into prose and has no
per-article structure to jump to, so its items are listed at the foot of the section as *reference* instead.
This is why `isVerbatimSection` earns its keep a third time.

Corollary cleanup: the per-section footer list is now suppressed for verbatim sections. Their titles already
appear as article headings **and** in the Contents; a third copy at the foot was noise.

### One more regression caught, and a real feature recovered

Rendering the chrome surfaced that **markdown images were leaking as literal text** — `![Image 16](https://…
"caption")` printed verbatim mid-article. Two causes, both introduced when §9b stopped flattening markdown:

1. `ANY_IMAGE` was `^!\[[^\]]*\]\([^)]*\)$`, which stops at the first `)` — and these captions contain
   `(International)`. It also never handled the form extractors actually emit for a gallery: the image
   **wrapped in a link** to its full-size copy, `[![alt](img)](href "caption")`.
2. Even once matched, `imageTag` swallowed every URL-bearing image. That rule is right for AI-written prose,
   where a model-authored image URL is fabrication by construction — but wrong for a verbatim article body,
   where the image came out of the author's own page along with the words. Split by a new
   `RenderOpts.trustImageUrls`, defaulting to **false** (the safe direction).

The result is not just "no litter": **"Art worth looking at" now shows the art.** It had been an all-text
section about photography because every photograph was being dropped as a safety measure meant for a
different code path.

### Verified

Issue 15 rebuilt end-to-end: 13 `h3` anchors = 13 items, 17 TOC links, 4 sticky headers, 4 images rendering,
0 stray underscores, 0 literal `---`. Jumping to `#f_art-2` lands on the article whose title the TOC showed.
`tsc` + `next build` green.

### Known remaining

## 12. Truncation that admits itself (item 6)

`fetch.ts` and four source adapters each capped a body with a bare `slice()`, which cut mid-word — *"…never
to prostitute my press to the purposes of cor"* — and said nothing about it. The reader cannot tell a piece
that **stopped** from a piece that **ended**.

`truncateAtBoundary(text, max)` now cuts on a paragraph break, falling back to a sentence end, then a word,
and leaves a mark. All five cap sites go through it.

### Why the mark lives in the stored text

`digest_posts.body` is a cache that outlives the run that filled it. A `truncated` flag on the in-memory
`Item` would be lost the moment a later issue reused a cached body — precisely when the reader is still
looking at a half-article. So the marker is part of the text, and `renderRawList` turns it into
`[Read the rest at {source} →](url)`.

### The sentinel had to be a character that cannot occur in prose

The first version used `[…]`. The verification harness caught the collision immediately: that is the
standard **editorial mark for elided text**, and a Carl Jung quotation in this very issue contains one —

> The question of the meaning and worth of life never becomes more urgent … than when we see the final
> breath leave a body which a moment before was living.
>
> [`[…]`]
>
> Life is an energy-process.

A body ending in a genuine elision would have been silently relabelled "Read the rest at …" — **a fabricated
claim about where the article went**, which is the one class of error this pipeline exists to prevent. The
mark is now `U+E000`, a Unicode private-use codepoint: reserved by the standard for exactly this, an in-band
marker with no in-band meaning.

Worth naming the general rule, because it recurs: **an in-band sentinel must come from a namespace the
content cannot use.** Choosing a "sufficiently unlikely" readable token is choosing a rare silent failure
over a loud impossible one.

### Verified

5 boundary assertions (short text untouched · paragraph break · full stop retained · closing quote retained ·
a genuine `[…]` in the body is *not* mistaken for the mark) plus "the mark survives `cleanBody`". End to end
on issue 15: the genuine editorial ellipsis is preserved, **0** false "Read the rest" links, **0** sentinels
leaked to the page. `tsc` + `next build` green.

### Known remaining

One literal `[![Image 6](h` is still on the page: it is baked into a **stored body** that the old `slice()`
already cut in half. New fetches will not produce it; that row clears when it is next re-fetched. Not worth a
migration — but it is the reason the corpus cache and the extraction logic want the `trim_version` treatment
described in §5.

## 13. The trim pass, built (item 7)

Ruling recorded: **the trim pass is not gated on `ai_enabled`.** That flag gates *voice* — whether a model
writes prose for the reader. A pass that provably cannot introduce a word is hygiene, and the
subsequence guarantee below is what earns the exemption.

### Shape, as designed in §5

`lib/digest/trim.ts`. Body → numbered paragraph blocks → model returns `{"drop": [{i, starts, why}]}` →
**this file does the deleting.** Output alphabet is integers, so the result is provably a subsequence of the
input and output stays ~40 tokens regardless of article length. Cached on `digest_posts.body_clean` with
`trim_version`; `body` is never overwritten, so it is reversible and re-runnable when the prompt improves.
Runs in `buildSection` *after* the per-section cut, so a feed offering twenty posts for a four-item section
is never billed for the sixteen nobody will read.

### What measuring it changed

The design survived contact; the prompt did not. Run against real stored bodies, the first version **deleted
a real content paragraph**:

> `drop [7] ad :: [James Stockdale](youtube.com/…) was held captive in Hanoi, North Vietnam. He was sent to
> a war camp famous for its brutal treatment of prisoners.`

It saw a YouTube link and inferred advertisement. That is the exact failure this pass must not have, and no
length heuristic separates it from a real CTA — *"To learn more, check out Ryan's interview…"* is the same
size and shape. The difference is what the block is **doing**, so that is what the prompt now tests:
*a link is not an advertisement; drop a promotional block only when promotion is all it does.* The Stockdale
paragraph survives; the CTAs still go.

Two mechanical backstops around the judgement:

- **Echo verification.** The model must copy back each dropped block's first four words, and a drop whose
  echo doesn't match its number is discarded. This guards **index drift** — the model miscounting and
  deleting the paragraph *next to* the one it meant. A semantic mistake is a judgement call; an off-by-one is
  a silent hole.
- **A ceiling on deletion.** Refuse to cut more than half a body. This fires on real data: the model
  correctly identified 15 of 18 blocks of a *"Happy 1st Birthday, Atomic Habits!"* post as pitch, and 7 of 8
  of the Stoicism Today migration notice. Applying that leaves a stub that reads worse than the honest
  promotional post — and hides the actual finding, which is that **those items should not have been selected
  for the digest at all.** Furniture removal is this stage's job; deciding an item doesn't belong is the
  selector's. Past the threshold the body is kept whole, the intended drop list is still recorded, and the
  signal is logged rather than swallowed.

### Correcting §5

§5 predicted this pass would handle the Substack migration notice — "a blocklist cannot catch *this whole
piece is administrative*". It **identifies** it (7/8 blocks, `admin_notice`) but deliberately **does not
delete** it, because the ceiling holds. The residue that motivated the model pass turns out to be a selection
problem wearing a trim problem's clothes. That is a better outcome than the one predicted, but it is not the
one predicted.

### Measured

On the sampled bodies, after the guards: **−4.7%**, and every surviving drop is furniture — leftover
cookie-consent blocks the deterministic list missed, a Hyperallergic membership pitch, a *"Available as a
print"* shop CTA, two Daily Stoic course promos. Zero content paragraphs removed. Migration
`20260803170000_digest_posts_trim.sql` pushed; `body_clean` / `trim_version` / `trim_drops` live.

### Honest limits

- Verified against the **real prompt, block numbering, parse and apply logic**, with only the provider call
  stubbed — `llm.ts` transitively imports `next/headers` and can't be loaded outside Next. The pipeline
  wiring (`buildSection` → `trimItems` → DB round trip) is typechecked and built but has **not** been run
  end to end against a live issue.
- The pass is non-deterministic. `trim_drops` is the audit trail for when it gets one wrong, and `body` is
  always there to fall back to.
