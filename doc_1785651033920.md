# The digest agent — design

> Answering two questions: (1) how one agent serves both "do this specific thing" and "walk me
> through building the whole digest", and (2) how the thread stays small and *true* across a long
> session where the underlying configuration keeps changing.

## 0. BLUF

Three commitments, everything else follows:

1. **The agent is not a second client of the domain — it's the same client wearing a different
   adapter.** Forms and tools both compile from `sectionSchema.ts` and both land in one
   `applyCommand()`. "Mirror" becomes a *derivation*, not a discipline you have to maintain.
2. **Objectives are derived, never stored.** A pure `digestReadiness(digest, issues, posts)` computes
   "what's wrong / what's next" from data you already have. It is injected as an **anchor** and only
   when the user's message has no concrete ask. One agent, two context recipes, chosen per turn.
3. **The thread is not the memory.** State is re-hydrated from the DB every turn and stripped from
   history; only *preferences* survive folding. Tool results collapse to receipts after one turn.

And one negative commitment: **do not port `book_agent_runs` / self-chaining / the pg_cron
watchdog.** That machinery exists to survive Supabase's ~150s worker ceiling. This app is Next.js on
Vercel Fluid Compute — 300s, streaming on the Node runtime, no chaining needed. Copying it would be
importing a workaround for a constraint you don't have.

## 1. What "the UI's mirror" has to mean structurally

The naive reading of "everything the user can do, the agent can do" is a checklist you maintain by
hand. That decays: someone adds a field to `ranked`, the form gets it, the tool doesn't, and the
agent quietly writes an invalid section. This repo has already been bitten by exactly that shape —
it's the **multi-mirror drift** that `sectionSchema.ts` (and `dnaSchema.ts` before it) was introduced
to kill.

So make the mirror mechanical.

### 1a. Tools compile from the schema you already have

`SECTION_FIELDS` is pure data with `type`, `required`, `requiredWhen`, `hint`, `options`. That is
already 90% of a JSON Schema. One function:

```ts
// lib/digest/agent/tools.ts
toolFor(kind)  →  { name: `add_${kind}_section`, input_schema: jsonSchemaFrom(fieldsFor(kind)) }
```

`hint` becomes the field `description` — the *same sentence* that tells a human what the field means
tells the model. Add a field to a kind, and the form, the server parser, and the agent tool all gain
it in one edit. That is the property worth paying for.

Open choice: one fat `add_section` with a `kind` discriminator (fewer tools, model must pick the
right branch) vs. one tool per kind (11 tools, each unambiguous). Recommend **per-kind**: the model
picks a source by *name*, which is the decision it's actually good at, and each schema stays small
and required-complete.

### 1b. One command layer under both adapters

Today `actions.ts` is FormData-shaped: `str(form, key)`, `Number(form.get("id"))`. The agent has
JSON. Don't make the agent synthesize FormData, and don't fork the write.

Extract the **command layer** (ports-and-adapters / hexagonal): a small set of pure-ish functions
taking typed input and doing the read-modify-write.

```
 forms (RSC)  ──FormData──► adapter ─┐
                                     ├──►  applyCommand(cmd, ctx)  ──►  digests row (sections jsonb)
 agent tools  ──JSON──────► adapter ─┘            │
                                                  └── one place for: validation, RLS client,
                                                      revalidatePath, audit row, inverse-for-undo
```

Commands, v1 — exactly the current UI surface, nothing invented:

| command | UI equivalent | risk |
|---|---|---|
| `create_digest` | `/digests/new` | safe |
| `update_digest` | Settings tab | safe (but `web_search_enabled` / `ai_enabled` spend money) |
| `add_section` / `update_section` | Sections tab | safe |
| `remove_section` | remove link | **destructive** |
| `preview` | Preview button | **spends tokens**, ~20–70s |
| `run_now` / `regenerate` | Run now button | **sends mail**, marks seen |
| `forget_message` | Inbox | **destructive** |
| `connect_readwise` | `/settings` | credential — agent should *route*, not collect |

Reads the agent needs that aren't writes at all — and these matter more than the writes, because
they're what lets the agent reason instead of guess:

`read_digest`, `read_issue(n)`, `read_posts({used, source, older_than})`, `read_inbox`,
`readiness()`. `read_posts` is the sharp one: the unused half of `digest_posts` is the evidence for
"this feed isn't earning its place", and the corpus already records the **age of the writing**. An
agent that can run that query can say "James Clear's feed has served you writing averaging 6.8 years
old across 4 runs — drop it?" No UI affordance today produces that sentence.

### 1c. Mirror = capability parity, NOT authority parity

The DNA side's standard is "the agent proposes, the author applies" — right there, because a bad
prose write destroys work. Digest config is different: it's jsonb in one row, cheap and reversible.
So invert the default and move the gate to where the real cost is:

- **direct write** — everything in the config surface (sections, name, voice, cadence)
- **confirm** — destructive (`remove_section`, `forget_message`, `regenerate`) and money-spending
  (`preview`, `run_now`, turning on `web_search_enabled` / `ai_enabled`)
- **undo** — because every write goes through one command layer, storing the inverse is cheap.
  A `digest_agent_events` row per applied command is both the audit log and the undo stack.

Consequence for the UI: writes must show up without a refresh (the house **refresh-is-a-no-op**
standard). Friction worth naming: that standard was built for the Vite SPA + Supabase Realtime. This
app is RSC + server actions, so the same guarantee is `router.refresh()` from the client when a
write-tool result streams back — or a Realtime subscription on the `digests` row if you want the
list to move while the agent is mid-turn. Pick one deliberately; don't let it be an accident.

## 2. Question 1 — two objectives, one agent

### The failure to avoid has a name: intent pollution

If you always inject "your job is to walk the user through building a digest", then a user who asks
"why was section 3 empty yesterday?" gets an agent that answers *and then wanders off* into
onboarding. If you never inject it, "help me build this" gets an agent with no idea what "built"
means.

This was already solved once here, on the DNA side, and the answer transplants cleanly:

- `currentObjective()` — a **pure derivation** of "where you are" from the data, never a stored
  wizard step.
- injected as an **anchor, not a fence** — it biases the default action, and is explicitly
  subordinate to a concrete ask.
- under a **three-state injection policy**: `inject = autoMode || userAskedToBeGuided || !ask.trim()`.

### `digestReadiness()` — the digest's version

One pure function over data you already store. Nothing new to migrate, nothing to backfill; adding a
check is adding a term.

```ts
readiness(digest, sections, lastIssues, posts) → { blocking: Note[], degrading: Note[], next: Step }
```

Blocking (the digest cannot produce anything worth reading):

- zero sections
- `active = false`, or `deliver_at`/`timezone` never set
- no `kindle_email` on the account
- a `readwise` section with no verified token → **silently skipped at 6am**
- a `search` or `prompt` section with `ai_enabled = false` → **silently skipped at 6am**
- a `search` section with `web_search_enabled = false`

Degrading (it will deliver, but it'll be bad) — this is the half only the corpus can see:

- a feed whose median item age is > 6 months (measured: James Clear 6.8y, Daily Stoic 3y)
- a section that produced zero items on the last N runs (a dead beat, or a narrow one on a daily
  cadence — the README's own "narrow beats produce empty days")
- a source with a hit rate near zero in `digest_posts` (pulled a lot, used never)
- never previewed / never delivered

Note the shape: this is the **lint set** pattern from the DNA side, not a wizard. It's stateless, it's
queryable, and — importantly — it's useful *without* an agent. Ship `readiness()` first and render it
as a banner on the Sections tab; the agent then consumes the same function. **The agent should be the
second consumer of every capability, never the first.** That's what keeps it from becoming the only
way to use the product.

### The routing, per turn

```
user message
   │
   ├─ has a concrete ask?  ──yes──►  system + <digest_state> + <standing_prefs>          [task mode]
   │                                 (readiness available as a TOOL, not injected)
   │
   └─ vague / "help me build" / ──►  system + <digest_state> + <standing_prefs>
      "keep going" / auto-mode                + <suggested_next>                       [guided mode]
```

Two things make this feel like one agent rather than a mode toggle:

1. **`readiness()` is always available as a tool** even in task mode. So "why was it empty?" can pull
   the diagnosis without the standing objective sitting in the prompt steering the turn.
2. **Guided mode emerges from task mode at the close.** After any successful command, the closing
   line offers the top derived step: *"Added. Two things still make this silent at 6am — the Readwise
   section has no token, and web search is off for your `search` section. Want me to sort those?"*
   The user never picks a mode; the checklist surfaces itself as a consequence of doing work.

### The objective that actually matters: preview is the loop

The DNA agent's weakness is that it can't taste its output. This one can. `preview` is
**side-effect-free** (no mail, no issue row, no seen-marks), goes through the *same* `compile()` as
the 6am job, and returns headers (`x-digest-sections`, `x-digest-items`).

That converts "help me build my digest" from form-filling into a real **generate↔verify loop**:

```
   propose sources ──► preview ──► READ the output ──► judge against the user's stated taste
        ▲                                                        │
        └──────────────── adjust (cadence, max_items, voice) ◄───┘
```

This is the whole argument for a digest agent over a better form. A form can't notice that the
section it just helped you configure produced two paragraphs of aggregator slop. Constraints:

- `preview` costs tokens and 20–70s → **budgeted**: confirm the first one, then cap at N per session,
  and log it to `ai_calls` like everything else (it already logs with `task_id = null`).
- the agent should default to `?ignoreSeen=1` when previewing right after a real send, or it will
  correctly dedupe to nothing and mistake a working pipeline for a broken one.
- a preview response is 5–10k tokens. That's the single biggest context pressure in the system — see
  §3b.

## 3. Question 2 — context that stays small *and true*

The framing that unlocks this: **there are two kinds of things in a thread, and only one of them
should ever be replayed.**

| | example | lifetime | where it belongs |
|---|---|---|---|
| **State** | "there are 4 sections; the second is a `feed` on 3 urls" | until the next write | the **database**, re-read every turn |
| **Intent** | "nothing older than six months"; "I hate hype"; "keep it short" | forever | a **durable prefs block** |

Replaying state as conversation is not merely wasteful — it is **wrong**, because the user may have
deleted that section in the UI two minutes later. That is precisely the failure in your question:
*"the context has changed, but the user hasn't started a new session."* The fix isn't better
summarization. It's **not storing state in the transcript at all**.

### 3a. The per-turn prompt recipe

Ordered deliberately — static first so the prompt cache has a stable prefix, volatile last.

```
[static  ] constitution + tool schemas          ← never varies → cached prefix
[derived ] <digest_state>     SELECT, fresh     ← ~1k tok, AUTHORITATIVE, kills stale history
[durable ] <standing_prefs>   accreted, editable ← ~200 tok, survives session boundaries
[cond    ] <suggested_next>   readiness()       ← only when the ask is vague (§2)
[window  ] last ~6 turns verbatim
[fold    ] rolling summary of older turns — PREFERENCES ONLY, never config facts
```

`<digest_state>` cannot be stale by construction, because it's a query, not a memory. That one move
retires most of the trimming problem: you're no longer trying to decide which old assertions about
configuration are still true — you've stopped letting the model form beliefs from them.

### 3b. Tool-result elision (the real token hog)

In a tool-loop agent the transcript is dominated not by user text but by **tool results**. One
`preview` is 5–10k tokens; three previews in a session is more context than everything the user typed
all week.

Rule: **a tool result is retained in full for exactly one turn, then collapses to a receipt.**

```
turn n    : preview → <full issue html/markdown, 8k tok>
turn n+2  : preview → "[preview #3 · 4 sections · 11 items · 2 empty · 41s]"
```

This is safe *only because the payload is retrievable* — previews and issues are rows; `read_issue(n)`
gets it back. That's the general principle and it's worth naming: **retrieval over recall. Anything
the agent can fetch on demand should not be resident in context.** (Your PM roadmap already has
"deterministic context hydration" as a Later item — this is the same idea, applied to the digest.)

### 3c. Summarization with a retention *policy*, not a length target

When older turns fold, the summarizer is not asked to "summarize." It's asked to extract exactly one
category:

- **KEEP** — stated preferences, taste, corrections, rejected options *and why they were rejected*
  (the last one matters: without it the agent re-proposes what you already turned down)
- **DROP** — every assertion about configuration; every tool call and result; every "done, added ✓"

Adopt the house rule the DNA side already ratified as NORTH_STAR §6 #8 — **accept/deny is a state
change, not an erasure.** A denied proposal stays legible in the chat UI for the *human*; it just
doesn't need to stay in the *model's* context beyond "rejected `search`, too expensive."

### 3d. The staleness fence — one cheap line

Even with fresh state, an old turn can say "I added the Stratechery feed" about a section that no
longer exists, and the model can reason from it. Cost of prevention: one line.

Stamp each message with a config version (`digests.updated_at`, or a section counter). When building
the prompt, if the current version is ahead of the version at the fold point, emit:

```
<note>The configuration changed since earlier in this conversation.
Earlier statements about sources may describe a state that no longer exists.
<digest_state> below is authoritative.</note>
```

This is the same idea as the `src_hash / prev_hash` chain on the incremental prose digest: a cheap
invalidation marker beats an expensive reconstruction.

### 3e. Session boundaries — design so it doesn't matter

Don't rely on the user starting a new session; they won't, and that's your question. Two moves:

- **Make long sessions degrade gracefully** (3a–3d do that). A 200-turn session should have roughly
  the same prompt size as a 10-turn one.
- **Offer a boundary; never impose one.** When both the topic changes *and* the config version has
  moved, surface a "start fresh?" chip. A chip, not a modal.
- Archive sessions to their **own table**, not an unbounded jsonb column on the run row — the DNA side
  already paid for that lesson (slow "New chat", REPLICA-FULL Realtime amplification).

### 3f. Measure it, don't feel it

`ai_calls` already records `input_tokens` per call with `source = "digest"`. Set a budget and watch
the number:

- system + `<digest_state>` + prefs ≤ ~3k
- history window + fold ≤ ~6k
- cache-read ≫ fresh input on turns 2+ (if it isn't, the static prefix isn't stable — check block
  ordering)

Same gate the PM roadmap already set for the book agent. Context policy designed by feel drifts;
context policy with a query on it doesn't.

## 4. Runtime — what NOT to copy

| DNA agent (Supabase edge) | why | digest agent (Vercel) |
|---|---|---|
| self-chaining, one call per link | ~150s worker ceiling | **not needed** — 300s default, one streaming request |
| `book_agent_runs` durable row + `pending` | must survive the chain | a row for *history*, not for resumption |
| pg_cron watchdog reviving stalled rows | chain links die silently | **not needed** |
| `CHAIN_SECRET`, `verify_jwt = false` | server-to-server chaining | **not needed** |

What *does* carry over: one thread per digest, the slash-command sugar, `ask_user` to park on a
genuine fork, and a single stop path.

Model routing: the agent loop wants tool use, so it's Anthropic — `llm.ts` deliberately **throws** if
a DeepSeek model is handed `tools`, and that guard should stay. Extend the chokepoint with a
`callModelLoop()` rather than reaching for AI SDK's `streamText` directly; the one-chokepoint
invariant (`ai_calls` gets every call) is worth more than the convenience. If you do use the AI SDK,
log from `onFinish` — don't let the agent become the one AI surface with no cost attribution.

Preview is the wall-clock risk: agent turn + a 70s preview must fit in 300s. If it ever doesn't, the
answer is Vercel Workflow or Queues, not a hand-rolled chain.

## 5. Build order

Each rung is independently useful — nothing here is only valuable once the agent exists.

1. **`readiness()` + a banner on the Sections tab.** Pure function, no agent. Immediately tells you
   which sections silently skip at 6am. *Success: a digest with a tokenless Readwise section says so
   on screen instead of at 6am.*
2. **The command layer.** Refactor `actions.ts` into FormData-adapter + `applyCommand`. No behavior
   change; the forms keep working. *Success: `pnpm build` green, the UI unchanged.*
3. **Tools generated from `sectionSchema`** + the read tools. Test them from a script, no chat UI.
   *Success: a script adds a valid `ranked/arxiv` section and rejects one missing `targets` — with
   the same error text the form gives.*
4. **The loop + rail UI**, task mode only. No objective injection, no summarization. *Success: "add a
   Stratechery feed and preview it" works end to end.*
5. **Context policy** — 3a–3d. *Success: turn 40's prompt is the same size as turn 5's; `ai_calls`
   proves it.*
6. **Guided mode** — inject `<suggested_next>` under the three-state policy, plus the closing-line
   offer. *Success: "help me set this up" walks a cold digest to a preview the user says yes to.*

Steps 1–3 are worth doing whether or not the agent ever ships. That's the test of whether the
architecture is right.

## 6. Named tradeoffs

- **Per-kind tools vs. one `add_section`.** 11 tools cost prompt bytes in every call; one tool costs
  correctness. Recommended: per-kind, because the schemas are small and required-completeness is the
  thing that keeps a broken section from being saved.
- **Direct write vs. proposal channel.** Diverges from the DNA house rule. Justified by cheap,
  reversible jsonb — but it *is* a divergence and should be written into `pm/DECISIONS.md` as one, not
  discovered later as an inconsistency.
- **Fresh `<digest_state>` every turn vs. prompt caching.** A volatile block after a static prefix is
  the right ordering, but it does mean the cached prefix ends before it. Accept it; verify with the
  cache-read ratio.
- **Elision assumes retrievability.** Every elided payload must have a tool that fetches it back. If
  you ever elide something with no `read_*` route, you've created amnesia, not compaction.
- **Agent-added sections bypass the form's own hints.** The form's `hint` text is how a human avoids
  a bad config; the model gets the same text, but nothing stops it choosing a plausible-looking
  `min_score`. Mitigation is the same as for humans: `readiness()` + preview, not more prompt.
