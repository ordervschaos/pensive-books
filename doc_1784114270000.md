# RAG in the book-agent — mechanics & trade-offs

## Thesis

The agent already does two of the three things people mean by "RAG." The book's own
content does **not** need it. The one place RAG earns its keep is a durable
craft/reference knowledge base — and its skeleton already exists in
`_shared/research.ts`.

---

## RAG decomposed (five stages)

1. **Chunking** — split a corpus into retrievable units. The unit *is* the retrieval grain.
2. **Embedding** — chunk → vector (point in ~384–1536-dim space; nearness ≈ meaning).
3. **Indexing** — store vectors for fast **ANN** (Approximate Nearest Neighbor). Supabase =
   `pgvector` + **HNSW**/**IVFFlat** index.
4. **Retrieval** — embed query the same way → **top-k** by **cosine similarity**. Optional
   **hybrid** (lexical BM25/`tsvector` + vector) + **rerank**.
5. **Augmentation** — inject retrieved chunks into the prompt. `context.ts` already does this
   with `<craft_notes>`.

**Whether to RAG at all** — the three-part test. RAG pays off only when ALL hold:
- (a) corpus **bigger than the context window**,
- (b) knowledge **not reliably in the model's weights**,
- (c) content **selectable by query relevance**.

---

## The three corpora

| Corpus | Size | (a) fits? | Address by | Verdict |
|---|---|---|---|---|
| **1. Book DNA** (nodes+prose) | ~200 nodes, few 100 KB | fits → RAG fails (a) | known handle (id/name/motif) | **No RAG.** `read_node` (structured) + `search_nodes` (lexical) dominate. Also a *hot mutating* corpus → an index would be perpetually stale. |
| **2. Curated tier-1 craft** (`craft-kb.ts`) | small, **always relevant** | fits | — | **In-context injection** (what you do). Not RAG. |
| **3. Open-world craft/genre/reference** | unbounded | ✗ | query-selectable | **RAG passes all three.** Currently `research_web` + `craft_notes` = *agentic RAG, no persistent index*. |

Key lesson: **retrieval strategy is a function of corpus size × how you address the corpus.**
Small + addressable-by-name → grep beats vectors. Large + addressable-by-meaning → embeddings.

## The system (today)

```
author ask ──► book-agent turn (context.ts threadSystem)
                 │  injects: whole DNA tree DIGEST + brief + craft_notes + skills
                 │  tools: read_node (structured, by id)   ← retrieval
                 │         search_nodes (lexical grep, all fields incl prose) ← retrieval
                 │         research_web (LIVE web search → distill → save craft_notes) ← agentic RAG
                 ▼
       books.craft_notes  ◄──── dna-research (PRECOMPUTE, option B)
       (per-book cache, author-editable, re-injected every turn = augmentation)
```

Two retrieval modes already exist over the book (structured + lexical). One agentic-RAG
mode already exists over the web (live, per-query). What's missing: a **persistent, cross-book
index** so web knowledge accumulates instead of being re-searched per book.

---

## The four trade-offs (decisions, not facts)

1. **Lexical vs semantic** — grep is exact/cheap/explainable/zero-infra, fails on synonymy.
   Embeddings recall by meaning, blur precision, cost a model call + index. Lexical when you
   know the *term*; semantic when you know only the *meaning*.
2. **Stuff vs retrieve** — stuffing has *no retrieval-miss failure mode* and is cheap on a
   cache-stable prefix; bounded by window + "lost in the middle." Retrieve only when it can't fit.
3. **Precompute vs live** (your option A/B, already in `research.ts`) — index/cache is out of
   hot path, inspectable, editable, can go **stale**. Live is fresh, slow, non-deterministic.
4. **Retrieval's hidden cost** — a *miss* makes the model **confidently blind, silently**.
   Stuffing degrades gracefully; retrieval degrades catastrophically and invisibly. Respect this.

## Minimum build (the one place worth it — Corpus 3)

Extend `research.ts` from live-only to **live + indexed memory**:

- **Table** `craft_chunks(id, embedding vector(384), text, source, tags, book_id nullable)`.
  `pgvector` already enabled (baseline dump line 52) → one migration.
- **Embed on ingest, never hot path.** Ingest path = existing `research_web`/`dna-research`:
  when it distills web results, also chunk + embed into `craft_chunks`. Knowledge accumulates
  across books.
- **Embedding model** = Supabase Edge built-in **`gte-small`** (384-dim, in-worker, no external
  key). Sidesteps DeepSeek/OpenRouter not serving embeddings.
- **Tool** `search_craft(query)` → top-k over `craft_chunks` → same `<craft_notes>`-style block.
  Agent flow: try the index first (fast, free) → fall back to `research_web` (live) on a miss.

Reuses the option-A/B architecture; adds one table + one embed step + one tool. RAG placed
exactly where all three preconditions hold.

## Explicitly NOT recommended

- Vector-indexing the book's own nodes/prose: fails precondition (a), hot mutating corpus,
  and lexical/structured retrieval already wins for retrieval-by-known-handle.
- Semantic `search_nodes` ("find by vibe"): the only real gap grep can't cover, but marginal —
  defer until a concrete miss motivates it.
