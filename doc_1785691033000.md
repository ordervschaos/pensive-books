# The DNA agent, read through the 2026 agent-eval framework

*Analysis of `supabase/functions/book-agent/**` + `scripts/eval-*` against Confident AI's "LLM Agent
Evaluation Metrics in 2026" (task completion / step efficiency / tool correctness / argument correctness /
plan quality / plan adherence / reasoning / component-level / tracing).*

---

## BLUF

**You are further along than the article's stack in three places and behind it in two.**

Ahead: your task-completion metric is a *deterministic product gate*, not an LLM judge; you already run a
pairwise preference judge with position-bias cancellation; and you've turned evals into **in-loop tools**
(`check_against_contract`, `read_shape`, `read_facts`, `read_confusion`) rather than offline scorers.

Behind: **zero tool-correctness / argument-correctness coverage**, and **zero component-level attribution** —
when a book comes out bad you cannot tell whether the *agent* chose wrong or the *dna-expand engine* generated
badly.

**The single highest-leverage gap is not on the article's list at all:** four LLM judges sit *inside the
control loop* and none of them has ever been calibrated. You measured ±0.25 judge noise on `read-logline`, an
*offline* judge where noise only mis-scores. The same noise on `read_facts` or the plan-gate **mis-steers the
agent**. Eval the evaluators first.

## 1. Where the DNA agent sits in the taxonomy

The article's ladder is Generator → Tool-calling → Planning → Autonomous. The DNA agent is **Level 3 with a
Level-4 mode**, but it doesn't fit the diagram cleanly, and the misfit is the interesting part.

| Article's diagram | DNA agent |
|---|---|
| LLM + Planner | `advance()` — one Claude call per turn, `threadSystem()` assembles the prompt |
| Tool Calling | 15 tools (`tools.ts`): 6 reads, 4 proposers, 3 judges, `ask_author`, `finish` |
| Memory | `book_nodes` tree (durable, the artifact) + `book_agent_runs.transcript` (episodic) |
| Monitoring | `ai_calls` — every model call, provider, tokens, cache, latency, error |
| Tool Evals → back into LLM | `check_against_contract` / `read_shape` / `read_facts` / `read_confusion` + `maybeInjectRenderVerify` |
| Response | a **proposal**, not an answer |

### The structural difference: the agent is a proposer, not an effector

`propose_node_ops`, `propose_expansion`, `propose_prose_render`, `propose_options` all **end the turn** and
park a reviewable object. A watcher (browser `useAutoAccept`, or `agent-build-run.mts` in Node) applies it and
resumes.

**Architectural term: `propose/apply split` — a human-in-the-loop actuator boundary.** The article assumes the
agent's tool call *is* the side effect. Yours isn't. Three consequences for evals:

1. **`applied` vs `discarded` is a free human-preference label on every production run.** The article tells
   you to sample production traces and have a human review them. You already have the human verdict, typed,
   on every proposal, in `book_agent_runs.steps`. Nobody is mining it. This is your regression-dataset pipe
   and it's already built.
2. **Tool-call latency ≠ task latency.** Your wall-clock includes an author round-trip that no metric family
   in the article models.
3. **Argument correctness has a repair loop, not just a score.** `persistRejection()` hands `validateOps`'
   rejection back to the model as the failing call's `tool_result`, siblings still execute, and the loop
   continues. That is strictly better engineering than the metric — but you never *count* it, so you can't
   tell a variant that gets it right first time from one that flails and recovers.

### Three things you have that the article doesn't mention at all

**a) Grader calibration (`--refs`).** Reference answers must score 10/10 before any real number is trusted. The
article's equivalent is "have a human spot-check the judge" — you made it a runnable precondition. This is the
thing that caught 7 of your 8 harness bugs.

**b) A user simulator with self-attribution signals.** `fallbackUses / nudges / repeats / ambiguous / pushes`
don't grade the agent — they tell you **whether to believe the grade**. `fallbackUses > 0` means the fixture
under-specifies; `ambiguous > 0` means the answer was chosen by rule ordering. The article has no concept of
"is my harness lying to me," which is precisely the failure mode you hit eight times.

**c) The A/B seam as a column, not a deploy.** `context_variant` + `variants.ts` with a contract-locked no-op
(`variants.test.ts`) means both arms ship in one deploy and trials **interleave** (`A,B,A,B`). Sequential
deploy-A-then-B is time-confounded by provider drift. The article says "run an A/B" and stops.

Plus `armVerified` — a guard that fails the whole suite if the variant never reached the model. Most eval
harnesses would silently report "no difference."

## 3. The gap the article doesn't name: your judges are in the control loop

The article's diagram draws **Tool Evals → back into the LLM**, then never discusses it again. You have
actually built it, at four sites:

```
check_against_contract  → plan + mandate conformance, agent-invoked
read_shape              → do acts deliver premise.shape.movements?
read_facts              → does this scene contradict established canon?
read_confusion          → cold read: could a first-time reader follow this?
maybeInjectRenderVerify → FORCE-injects a plan verdict after an applied render (auto mode)
```

This is **generate↔verify duality** — the agent sensing rather than dead-reckoning. It is the best idea in the
architecture.

**And every one of them is ungraded.**

You have hard evidence this matters: the same book, same text, same judge, twice → **5.0 then 4.75**,
`stakes_grounded` moved 5→4 on byte-identical input. For `read-logline` that noise costs you a wrong number in
a report. For `read_facts` it costs you **a wrong edit to the book** — the agent acts on the verdict.

Worse, `maybeInjectRenderVerify` is *forced* into the transcript in auto mode. A noisy verifier there is a
noise generator wired directly into a 100-turn autonomous loop. And you already know the failure mode by name:
the §v1 payoff-scoping fix exists precisely because false FAILs taught the agent to **dismiss verify**
("alarm fatigue"). You fixed one instance of a systemic problem you have no instrument for.

**Concrete ask:** the `--refs` pattern generalizes. Build reference fixtures for the in-loop judges — a scene
that provably contradicts canon, one that provably doesn't; an act set that delivers the movements, one that
doesn't. Run each judge N times on each. Report **mean, spread, and false-positive rate**. That is a
one-afternoon build reusing `eval-premise.mts`'s exact shape, and it is the highest-value eval you don't have.

## 4. Plan adherence: absent, and it's the product

`stageSubsteps("premise")` in `dna-journey.ts` is `interview (vision) → seed (logline) → premise (dramatic
question)`. The whole DNA thesis is that **the ladder is load-bearing** — a rung earns the right to the next
one.

Your grader asks *"did it reach the top?"* (`stageComplete`). It never asks *"did it climb, or scramble?"*

Climb violations that are cheap to detect deterministically from `book_agent_runs.steps` + `book_nodes`:

- proposed beats before the premise node was accepted
- `propose_prose_render` on a scene with no fresh sketch (the tool description says don't; nothing checks)
- `propose_node_ops` on a node whose parent is still a draft
- `replace_children` when `add` was correct, or the reverse (duplicate-node symptom)
- wrote a node's content without calling `get_schema` first — the tool description *says* wrong keys silently
  orphan the data, so this is a known, named, unmeasured failure

**This is the article's Plan Adherence metric, and unlike theirs it needs no LLM judge**, because your plan is
already data (`dna-journey.ts` + `PARENT_KIND` + `dnaSchema.ts`). Every rule above is a query.

## 5. Component-level attribution: the missing diagnostic layer

The article's strongest practical point: an end-to-end score tells you *something* broke, not *what*.

The DNA pipeline has at least six independently-failable components:

```
threadSystem()      → context assembly (digest, skill briefs, intent hydration)
advance()           → the agent's decision
dna-expand          → beatsheet / scenes / premise / contract / sketch GENERATION
prose stream        → the browser-side render (v2 pipeline + digest)
the judges          → read_*, plan-gate
applyNodeOps        → the write path
```

Today every eval is end-to-end on the thread. So when a 57-turn build produces a weak book, you cannot
separate *"the agent asked for the wrong beat sheet"* from *"the agent asked correctly and the engine
generated a weak one."* Those have opposite fixes — prompt the agent vs. prompt the engine.

`dna-expand` is the obvious first component to isolate: it's a pure function of (node, brief, target). Feed it
fixed inputs, grade the output with the existing judges, no agent in the loop. That single split turns "the
book is bad" into a two-way attribution.

## 6. What the article gets wrong about *your* cost model

The article assumes **tool-call count drives cost** (fan-out across MCP servers, hundreds of calls). Your §5a
diagnosis says otherwise:

```
average 75,463 UNCACHED tokens per call · ≈ $3.60/book
largest single contributor: the <book_state> digest — 108,702 chars (~27k tokens), re-sent every turn
```

Your cost is dominated by **preloading**, not by tool fan-out — and it is a *deliberate* design choice
(`withBookState` appends the live digest to the latest message so the model can't ground on a stale tree, which
by construction breaks the cache prefix at the same index no matter where you put it).

You are paying twice: a 27k-token whole-tree digest **and** `read_node`/`search_nodes`/`get_schema`. The 2026
practice is just-in-time retrieval — lightweight handles in context, detail on demand. Your `readsPerAiCall`
metric is exactly the counterweight that makes this tunable against evidence instead of argument. **No metric
family in the article names this trade.** Keep both bars; they're yours.

## 9. Ranked recommendations

1. **Meta-eval the in-loop judges.** Reference fixtures + N repeats + false-positive rate for `read_facts`,
   `read_shape`, `read_confusion`, plan-gate. They steer the agent; nobody has checked them. Reuses
   `--refs`. *(§3)*
2. **Plan adherence over the DNA ladder.** Deterministic rung-order + schema-before-write + sketch-before-prose
   checks, straight off `steps` + `book_nodes`. No judge needed. *(§4)*
3. **Tool correctness + rejection rate.** Per-fixture `expected_tools` / `forbidden_tools` (order-independent
   sets), plus count `persistRejection` events per tool. Both are ~30 lines against data you already store.
4. **Isolate `dna-expand` as a component test case.** Fixed inputs → existing judges, agent removed. Turns "the
   book is bad" into an attribution. *(§5)*
5. **Cost per graded outcome in the suite table**, and **mine `applied`/`discarded` from live runs into
   fixtures** — your production-failure→regression-test pipe is already instrumented, just unread. *(§1)*
