# Implemented: miner generalization Steps 1 & 2

Companion to doc_1783542000000.md (the implementation plan) and doc_1783541100000.md (the design). This
documents what was actually built and where.

## Step 1 — computed stylometric lints (`proseLints()`)

**Files**: `apps/web/src/features/dna/lib/novelDna.ts` + edge twin `supabase/functions/_shared/novel-dna.ts`
(byte-identical in the edited regions — verified with `diff` after editing).

- `LintConfig` gained two knobs: `emDashCeiling` (default `0.8`, per 100 words) and `cadenceSpreadFloor`
  (default `0.12`).
- **`em_dash_density`** (per scene): counts `—` and `--` in the scene's raw prose text (added a `text` field
  to the existing `SceneStat` precompute so the rule can regex the actual prose, not just the word-tokenized
  form), divides by word count, warns above the ceiling.
- **`cadence_uniform`** (book-level, one issue max): for every prosed scene, computes its own sentence-length
  coefficient of variation (same formula `monotone_rhythm` already used), then computes the **coefficient of
  variation of those per-scene CVs** — a second-order "spread of rhythm-shapes across the book" metric. Gated
  on ≥12 prosed scenes (`CADENCE_UNIFORM_MIN_SCENES`). One correction versus the plan doc's literal formula:
  when every scene's CV is identical (mean 0 included — e.g. every scene is individually flat), the naive
  `stddev/mean` is `0/0`; I special-cased that to `spread = 0` (maximal uniformity, should fire), rather than
  silently skipping the rule the way a bare guard would.

**Tests**: `novelDna.parity.test.ts` — added `pp_s8` (an em-dash-heavy scene) to the existing `proseBook()`
fixture, and a new 12-scene `cadenceBook()` fixture (identical flat-cadence scenes → spread 0). Both run
through the existing twin-parity harness (449 tests, all passing) plus two new targeted assertions. Ran
`tsc -p tsconfig.app.json` (clean) and `eslint` on the touched files (clean).

**Not yet done** (explicitly out of scope per the plan): the calibration gate — running `cadence_uniform` on
a human-authored EPUB import as a negative control to check whether 0.12 is the right floor. That needs an
actual imported human book in the DB; flagging it rather than guessing.

## Step 2 — scene technique fingerprint (read-side)

**Types** (both twins, in the `ValueCarrier`-adjacent block): new `SceneFingerprint` interface —
`closure` / `interiority_engine` / `motif_carrier` / `climax_cadence`, all optional enums. Added
`observed_fingerprint?: SceneFingerprint` to `SceneContent`, registered it in `OUTPUT_FIELDS` (so writing it
never spuriously stales a scene's plan-input hash) and in the three manual destructure sites that strip
output fields (`isProseStale`, `stampProse`, `sketchInputPlan`) — these don't read `OUTPUT_FIELDS`
dynamically, so they needed the same one-line addition each. `dnaSchema.ts` got a comment-only mention
(no `EditSpec` entry — it's a read-only output, never an editor field, same as `observed_value_carrier`).

**Edge fn** (`supabase/functions/read-facts/index.ts`):
- Added task (4) TECHNIQUE FINGERPRINT to the system prompt — unconditional (asked every scene, unlike
  value_carrier which needs a planned shift).
- Extended the JSON output contract with a `fingerprint` object; told the model every key is optional so it
  omits axes it isn't confident about instead of guessing.
- **Truncation fix**: `scene.prose.slice(0, MAX_PROSE_CHARS)` was head-only, which blinds `closure` (judged
  from the scene's ending) on any scene over 8000 chars. Changed to head+tail: first 6000 chars + `[…]` +
  last 2000 chars when over the cap.
- **Server-side allowlist**: four `Set`s (`CLOSURE_VALUES`, `INTERIORITY_VALUES`, `MOTIF_VALUES`,
  `CADENCE_VALUES|`), same pattern as the existing entity-id allowlist — an axis value that isn't in its set
  gets dropped (axis omitted from the object), never surfaced raw. The whole `fingerprint` key is omitted
  from the response if nothing survived validation.
- Deployed to the project (`supabase functions deploy read-facts`) under the standing deploy authorization.

**Client** (`factLedger.ts`): `FactReadResult` gained `fingerprint?: SceneFingerprint`; `invokeReadFacts`
threads it through both the bridge and edge-fn paths. `writeSceneLedger` gained a `fingerprint` param and
writes/clears it — **unconditionally**, unlike `observed_value_carrier`'s three-way branch (write / clear-if-
shift-scene / leave-untouched-if-shiftless), because the fingerprint task has no "doesn't apply to this
scene" case — every scene either gets a fresh verdict or the stale one is cleared. `runLedgerScan` passes
the new field through.

**Deliberately not touched**: `scripts/eval-bridge.mjs`'s `/read-facts` mirror — confirmed (via a research
pass) that it already lacks the R2/entity-grounding logic the edge fn has, consistent with the plan's note
that this mirror is intentionally not kept in sync. `factLedger.ts`'s bridge branch just returns
`fingerprint: undefined` there, which is the existing graceful-degradation pattern already in place for
`valueCarrier`.
