# Is a render call really "no-context"? — the agent→generator channel

**Answer: no.** The doc's "one-shot calls, nothing accumulates" is a claim about *state
accumulation*, not about *payload*. There is exactly one channel from the agent into the
generators, and it carries precisely the thing you suspected: knowledge that exists only in the
chat.

## The two supply lines into a render

| | Deterministic context | The editor's brief |
|---|---|---|
| Source | re-derived from `book_nodes` at call time | the agent's own words, this turn |
| Contents | scoped bible, ledger, seam, digest, sketch, disclosure budget | `focus` · `mustHonor[]` · `avoid[]` |
| Reproducible? | yes — same tree → same block | no — model-authored |
| Crosses a boundary? | no (both sides read the same store) | **yes** |

Architecturally: everything except the brief is a **blackboard** (shared datastore, no handoff
needed). The brief is the one **message-passed** payload, because it's the one thing not in the
datastore.

## Where it lives in code

- `supabase/functions/book-agent/tools.ts:95` — `propose_prose_render`'s `brief` schema. The tool
  description states the contract: *"the pipeline already has the voice, the mandate, and a
  continuity digest of every prior page; your job is to ADD what it can't compute."*
- `supabase/functions/book-agent/proposals.ts:90` — `sanitizeBrief`: trim, `focus` ≤ 400 chars,
  lists sliced to 12, `undefined` when empty. **Sanitization at a trust boundary** — the agent is
  an untrusted producer of context.
- `apps/web/src/features/dna/lib/agentThread.ts:59` — the brief is stored *on the proposal*, and
  replayed at apply time (`:210` sketch, `:218` expansion ops, `:235` prose).
- `supabase/functions/dna-expand/index.ts:618-628` — injection. Comment is explicit: *"AUGMENTING
  the deterministic context below, never replacing it."* Header text ranks it *"highest-priority
  guidance; it does NOT override the MANDATE or LOCKED facts."*
- `apps/web/src/features/dna/components/agentRail/ProposalCard.tsx:21` — the brief is rendered in
  the review card, so the handoff is auditable before Apply.

## Four properties that make it a channel, not a leak

1. **Serialized, not session-shared.** The agent's turn is finished, the author has clicked Apply,
   and the render streams *in the browser*. A shared session can't cross that; a serialized struct
   can. (This is forced by the **capability boundary** in §1 — prose is browser-orchestrated
   streaming a server-side tool loop physically cannot drive.)
2. **Additive, with a precedence lattice.** Brief > computed context, but brief < MANDATE/LOCKED.
   The agent buys *salience*, not *authority*.
3. **Bounded.** Caps and trims mean a runaway tool call can't bloat the prompt.
4. **Target-agnostic.** Not prose-only — a sketch or beat-sheet expansion carries one too.

## The tradeoff this surfaces

The author's raw chat message **never reaches the render**. It arrives only as whatever the agent
chose to distill. That is a **lossy compression channel with a model in the middle**: an
under-curated brief silently drops the instruction, and no downstream check can detect the loss
(the render can't know what it wasn't told). The only mitigation in place is *visibility* — the
brief shows in the proposal card, so the author can see what's about to ride along.

If this ever bites, the two candidate fixes are (a) pass the author's verbatim ask alongside the
brief as a second block, or (b) a post-render check that the ask's nouns appear — the existing
`check_against_contract` is the natural hook.
