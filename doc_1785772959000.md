# Explicit focus: promoting an implicit mode to a declared one

*Design note — 2026-08-03. Question: should the agent have an explicit, user-settable focus that
filters context, tools, and ambient information? How much of that is fencing vs anchoring?*

---

## 1. The finding that reframes the question

**The mode already exists.** It is derived, it already changes agent behaviour, and it is invisible
and unoverridable. Three pieces of live code:

- `_shared/dna-journey.ts` computes `DNA_STAGES` (premise → foundations → structure → scenes →
  draft) and, inside each, `stageSubsteps()` with per-substep `done` / `ready` predicates. The
  stage machine is **already built, already a twin (server + client), already tested.**
- `book-agent/context.ts` already branches on it. The `discovering` predicate pins the
  `vision-interview` skill and **suppresses ask-triggered skills**; `inInterview` forces objective
  injection; the three-state `injectObjective` rule decides whether the guided-flow anchor appears
  at all. That is mode-conditional context assembly — written as five ad-hoc predicates rather than
  one named concept.
- `book-agent/tools.ts:211` — `function threadToolsFor(): unknown[]`. It takes **no arguments** and
  returns a constant. The seam for parameterization is literally already cut.

So this is not "add a mode system to an agent that has none." It is:

> **Promote an implicit, derived, invisible mode to an explicit, declarable, visible one** — and
> replace five scattered predicates with one registry.

That is a far cheaper and far safer project than it first sounds, and the argument for it is mostly
an argument against *implicit* state, which is a much easier argument to win.

### The HCI name for the risk

A **mode error** (Norman; the thing Larry Tesler spent a career fighting) is when an actor performs
an action believing the system is in mode A while it is in mode B. Every modal interface risks it.
The classic antidotes are exactly two: **make the mode visible**, and **make exiting it cheap.**

Right now this system has the *worst* configuration — it is modal, but the mode is invisible and
cannot be exited. The author cannot see why the agent suddenly stopped offering options during the
interview. Making focus explicit does not introduce modality; it introduces the antidote.

## 2. Fencing vs anchoring — the wrong binary

"Is this fencing or anchoring?" splits too coarsely, because focus could control four different
things and they get four different verdicts.

| # | axis | what narrowing it means | verdict |
|---|---|---|---|
| 1 | **Visibility** — what the agent can SEE | a **scope fence** | **never.** This is precisely what was deleted in `agent-context-model.md`. |
| 2 | **Write permission** — what it may CHANGE | a **permission fence** | **never.** Locks are the only immutability; the review gate is the safety. |
| 3 | **Affordance** — which tools/skills are OFFERED | **relevance**, not a fence — *if* legible and escapable | **yes, with conditions** |
| 4 | **Salience** — which ambient blocks are injected, and scoped how | pure **curation** | **yes — this is the best part** |

Two observations follow.

**First: what was actually asked for is axes 3 and 4, not 1 and 2.** Re-read the proposal —
"filter the context and the tools", "ignore some ambient information", "the agent is actively trying
to fill the vision." Nothing in it asks to hide the tree or to forbid edits outside the focus area.
The instinct is already on the safe side of the line; it just needs the line drawn explicitly so it
stays there under future pressure.

**Second: axes 1 and 2 are exactly where the gravity pulls.** Once a mode object exists, someone
will eventually write `if (focus === 'scene') onlyAllowKinds(['scene'])`. That is how the deleted
design got built the first time. The line must be written down as an invariant, in the registry's
own comment, not merely intended.

### The precedent that proves axis 3 is legitimate

`agent-context-model.md` already ruled on this, when deciding what `agentCommands.ts` could keep:

> commands may keep an `available`/capability check used only to hide irrelevant commands — **that's
> relevance, not a fence**

And the deleted thing was specifically the *kind-write-fence*. The doc is explicit that the collision
was between two mechanisms — "context-as-filter" and "context-as-seed" — and that the filter had to
go because it fenced **writes**. Hiding an irrelevant tool was never the problem.

There is also a second precedent already shipped: prose generation is excluded from the agent's belt
as a **capability boundary** (it physically cannot drive a browser stream), not a scope boundary. The
system already ships a narrowed belt; nobody calls it fencing, because the narrowing is *about the
action*, not *about the territory*.

So the taxonomy in full:

```
                     narrows the TERRITORY          narrows the ACTION MENU
                     (what exists for the model)    (what it can do right now)

  permanent          ❌ scope fence  — deleted      ✅ capability boundary — shipped (prose)
  situational        ❌ never build this            ✅ affordance  — what focus should do
```

## 3. Ambient information is the strongest case

The follow-up point — *"in a focused task we'd ignore some ambient information and maybe just focus
on lints specific to that focus area"* — is the most valuable part of the whole idea, and it is
**100% curation with zero fencing**.

The system currently injects, every turn: the derived objective, the full lint report, the
between-scenes ledger, the hunger block, craft notes, craft overrides. All of it is ambient — none
of it is the ask. And the codebase has *already paid for this exact problem once*:

- `injectObjective` became three-state because a standing "do the next rung" instruction competed
  with a concrete typed ask.
- `<story_analysis>` ships with two different `note` framings because "a per-turn imperative here
  made the agent fix lints when the author asked for something else entirely."

Those are two hand-rolled fixes to one general problem: **ambient state competes with the ask for
salience.** Focus generalizes the fix instead of adding a third special case.

Concretely, `analysisText(nodes, {}, lintConfigForBrief(brief))` becomes
`analysisText(nodes, {}, lintConfigFor(brief, focus))`, and lints are filtered to those whose subject
intersects the focus area. In `draft-scene` focus on scene 14, you see the lints touching scene 14
and its promises — not the twelve pacing flags in Act 3. The rest are still one question away
("what else is wrong?"), which is the anchor-not-fence test: **removing something from the prompt is
only anchoring if the model can still get it on request.**

That test is the cleanest rule in this whole design:

> **Curation is anchoring when the omitted thing is still reachable. It becomes a fence the moment
> it is unreachable.** The tree digest passes (`read_node` reaches the rest). Scoped lints pass (a
> `run_lints` tool or a focus switch reaches the rest). A write-fence fails — nothing the model can
> say reaches past it.

The corollary is a build requirement, not a nicety: **anything focus hides must have a named way to
get it back**, and the system prompt must say what that way is.

## 4. The one real danger: a declared focus is stickier than a derived one

The derived objective at least advances on its own — it is recomputed from the live tree every turn,
so it self-corrects. A **user-declared focus does not.** Set focus to scene 14, come back tomorrow,
ask about the ending: now a stale declaration is actively fighting the ask, and it is *more*
dangerous than the derived objective ever was because nothing recomputes it.

Three mitigations, all of which the codebase can already support:

**(a) The ask always wins — unchanged.** Focus sets defaults for a turn with no concrete ask. The
`SYSTEM_THREAD` Task-discipline paragraph stays exactly as written. Focus never gets an imperative
framing; it gets the same treatment as `<current_objective>` — an anchor, not a leash.

**(b) Every focus carries a completion predicate.** This is the genuinely good idea hiding in the
proposal, and `dna-journey.ts` already has the machinery: every substep has `done` and `ready`.
A focus that knows when it is finished **self-clears** — the interview focus ends when
`brief.vision.compiled_at` is set; a scene focus ends when the scene has prose and passes verify.
The UI shows "focus complete → next: logline" rather than silently persisting. Staleness stops being
a user-discipline problem and becomes a computed one.

**(c) Derived proposes, user disposes.** This resolves the two-sources-of-truth problem (derived
stage vs declared focus) rather than leaving it to collide:

```
derived stage (dna-journey)  ──proposes──►  the default focus chip
                                                 │
author overrides / clears / narrows  ────────────┤
                                                 ▼
                                     declared focus (on the run row)
                                                 │
                                  expires on its own done() predicate
                                                 ▼
                                     falls back to derived
```

The declared value wins while it lives; it just cannot outlive its own completion.

## 5. What it looks like

**Focus = `{ mode, target, pinned[] }`** — three slots, not two (see §5a for why the obvious
two-slot shape is wrong).

- `mode` — a named goal: `wide` · `interview` · `logline` · `foundations` · `structure` ·
  `draft-scene` · `consistency-audit`. Drives skills, ambient lens, tool menu, opening framing.
- `target` — **0 or 1** node: what the mode operates *on*. Owned by the mode; the thing `done()`
  reads.
- `pinned[]` — 0..n nodes the author wants kept in view. **This already exists** as the context tray
  (`attachedIds` → the `<focus>` block). Owned by the author; survives mode changes.

The split matters because the proposal's three examples are not the same kind of thing:

| example | what it really is |
|---|---|
| "focused on the interview stage" | a **journey stage** — already derived, needs to be declarable |
| "working on this scene: sketch, prose, review" | a **subject** (existing tray) + a **mode** |
| "find inconsistencies across the beats" | a **task with a completion predicate and book-wide scope** |

The third is the one that proves the design. A consistency audit needs the **whole book visible** —
scoping its territory would break it outright. What it needs narrowed is only its *tool menu*
(reads + one propose path, no expansion engines) and its *ambient lens* (consistency lints, not
pacing lints). Same conclusion: narrow the menu and the salience, never the territory.

## 5a. How task focus and the node tray co-exist

The two mechanisms answer **different questions**, which is why they compose cleanly rather than
needing arbitration:

> **Mode answers "what am I doing?" The tray answers "what should I be looking at?"**
> Two things can only conflict if they answer the same question. These never do.

### The grammar

The cleanest way to hold it is as parts of speech:

```
   mode          target              pinned[]
   ────          ──────              ────────
   the VERB      the DIRECT OBJECT   the MATERIAL kept in view
   "draft"       "scene 14"          "Mara's profile, the smuggling thread"
```

This immediately exposes why a single flat `subjectIds[]` is wrong. Consider: mode is
`draft-scene` on scene 14, and the author *also* pins Mara's character node because her voice keeps
drifting. Flatten those into one array and:

- `done: sceneHasProse(subjectIds[0])` becomes **order-dependent** — detach and re-attach Mara and
  the mode's completion predicate now points at a character node;
- the UI cannot tell which chip is "the thing being written" and which is "reference";
- clearing the mode must decide whether to also drop Mara, and either answer is wrong.

The target is the **object of the verb**. The pins are **adverbial**. They are not the same slot.

### Different owners → different lifetimes

This is the practical consequence, and it settles every lifecycle question:

| | `target` | `pinned[]` |
|---|---|---|
| set by | the mode (usually implied by *how* you entered it — right-click scene 14 → "draft this scene" sets both at once) | the author, explicitly |
| cardinality | 0 or 1 (mode-declared: `draft-scene` requires one, `interview` forbids one, `consistency-audit` treats it as an optional starting point) | 0..n |
| cleared when | the mode clears | **never automatically** — the author removes it |
| survives a mode switch | no | **yes** |
| read by `done()` | yes | no |

"I want Mara's profile visible" stays true regardless of which task I'm doing — so the tray outlives
modes. That was already asserted in §6a ("subject tray survives abandonment"); the ownership split is
*why*.

### What each one drives

They are orthogonal in the policy layer and additive in the context layer:

| | `mode` | `target` | `pinned[]` |
|---|---|---|---|
| tools offered | ✅ | — | — |
| skills injected | ✅ | — | — |
| ambient **lens** (which lint families) | ✅ | — | — |
| ambient **scope** (which nodes' lints) | — | ✅ | ✅ **additive** |
| hydration into the prompt | — | ✅ edit-ready | ✅ content |
| `done()` | ✅ declares it | ✅ subject of it | — |

There is exactly **one** place they combine: **ambient scope is `target ∪ pinned`.** Pinning a node
means "keep an eye on this," so its lints belong in view even when the mode is targeting something
else. Everything else is independent — which is what makes this cheap to build.

### Hydration depth should differ

The target is the thing being *changed*, so it deserves the **edit-ready** treatment that
`<mentioned>` already produces (path + child counts + schema + prose), not the thinner treatment the
tray currently gets (bare content).

Worth noticing: today's code already hydrates *message-mentioned* nodes more richly than
*author-attached* ones — an asymmetry that reads backwards, since attaching is the stronger, more
deliberate signal. Introducing `target` is the natural moment to fix it: **target ≥ mentioned >
pinned** in hydration depth.

### The naming collision is itself a bug

Two different things are currently heading for the name "focus": the existing tray (whose XML tag is
literally `<focus>`) and the proposed mode. Shipping both under one word guarantees confusion in the
prompt, the code, and the UI.

Recommendation, done in the same change so no window exists where both are "focus":

- **"Focus"** = the mode/task. New tag `<focus_mode>`, plus `<target>`.
- **"Pinned"** = the tray. Rename the tag `<focus>` → `<pinned>`; the field stays `attachedIds`.

It's a one-line prompt change, but it *is* a prompt byte change — so it belongs behind the existing
`variants.ts` A/B seam rather than shipped blind.

### Each should be able to suggest the other

Both directions, both as suggestions (*derived proposes, author disposes*), never automatic:

- **Pin → mode.** Attaching a scene is a strong signal. Offer a chip: *"Draft this scene?"* Don't
  auto-enter the mode.
- **Mode → pin.** A mode may declare *recommended* pins (`draft-scene` → the POV character, the
  previous scene). Offer them; the author accepts. Never silently stuff the tray, or the author
  loses track of what they own.

### The UI

One strip, two visually distinct chip types — because they're distinguishable in the model, they
should be distinguishable on screen:

```
  [ ◆ Drafting · scene 14/80  ✕ ]     [ 📎 Mara  ✕ ] [ 📎 smuggling thread  ✕ ]
    └─ mode + target, one unit ─┘       └──── pinned: author-owned, persists ────┘
       clearing this exits the mode      clearing these changes nothing about the mode
```

### Storage and shape

- **State on the run row.** The run row *is* the process (`agent-runtime-architecture.md`); focus is
  process state, must survive worker death and self-chain links, and must be readable by any worker.
  `book_agent_runs.focus` as `jsonb: { mode, target, setBy: 'user'|'derived', setAt }`. Note
  `pinned[]` is **not** in here — `attachedIds` already lives on its own (author-owned, longer-lived
  than any run), and merging them would tie the tray's lifetime to the mode's (§5a).
- **Registry as policy-as-data** — `_shared/agent-focus.ts`, matching the idiom already used by
  `agent-skills.ts`, `craft-kb.ts`, and the structure templates:

```ts
{
  key: "draft-scene",
  label: "Drafting a scene",
  skills: ["render-brief", "scene-plan-craft", "prose-patch"],
  tools:  ["read_*", "propose_prose_render", "propose_expansion", "propose_node_ops"],
  target: "required",           // "required" | "optional" | "none" — see §5a
  suggestPins: (nodes, target) => [povCharacterOf(target), previousScene(target)],
  ambient: { lints: "scene-scoped", objective: false, betweenScenes: true, hunger: false },
  done: (nodes, focus) => sceneHasProse(nodes, focus.target),
  exitHint: "Ask for anything else and I'll suggest widening the focus.",
}
```

Everything a mode controls is declared in one literal. A new mode is one entry — the same property
that makes structure templates cheap.

### A simplification payoff, not just added complexity

Focus-driven skill selection makes the **regex trigger system partly redundant.** Today
`matchSkills(authorAsk)` guesses the job from vocabulary and needs the `discovering` override to stop
story nouns tripping the wrong playbook mid-interview. With a declared focus, the mode *states* the
job; triggers degrade to a fallback for ad-hoc asks inside a wide focus. Net complexity plausibly
goes **down** — and the ugliest predicate in `context.ts` (the four-condition `discovering` check)
becomes one registry lookup.

## 6. Build order

Ordered cheapest-and-safest first, so the risky part is only built if the cheap part proves the need.

**Slice 1 — legibility. Zero fencing of any kind.**
Surface the derived stage as a chip strip under the chat header. Let the author pin, clear, or
switch it. Feed the pin into the *existing* injection predicates (`injectObjective`, the
`discovering` override). Nothing is hidden from the model that isn't hidden today; the author simply
gains sight of, and a veto over, a mode that already governs the agent.
*Success:* the author can see which stage the agent thinks it is in, and can correct it when wrong.

**Slice 2 — the ambient lens. Curation only.**
`lintConfigFor(brief, focus)` plus subject-intersection filtering; per-mode toggles for the
objective / between-scenes / hunger blocks. Ship a `run_lints` (or equivalent) escape so anything
hidden is reachable.
*Success:* asking about scene 14 no longer drags Act 3's pacing flags into the turn; asking "what
else is wrong?" still returns everything.

**Slice 3 — the affordance. The only slice that narrows anything.**
`threadToolsFor(focus)` — the seam already exists. Non-negotiable conditions:
1. `read_*`, `ask_author`, and `finish` are **always** in the belt. Never fence the escape hatches.
2. The narrowing is **stated in the prompt**, with the way out: *"You are in draft-scene focus; the
   expansion engines aren't offered here. If the author needs one, say so and offer to widen."*
   A silent narrowing turns a model that would have routed around it into one that invents a
   workaround.
3. It is **never** a write fence. Any node may still be edited via `propose_node_ops`.

**Never build:** visibility narrowing, or write-permission narrowing. Write it into the registry's
header comment as an invariant, because the gravity toward it is real.

### Measurement

The A/B seam already exists (`variants.ts` / `variantSuffix`, appended last so it can override
anything above it) and `ai_calls` records provider, tokens, and latency per call. Focus is therefore
A/B-able from day one. The metric that matters is not token count — it is **on-task rate**: how
often a turn does the thing that was asked. That is the failure focus exists to fix, and the one
that regressions would show up in first.

## 6a. Exit: the load-bearing half

An exit affordance is not a convenience on top of focus — **it is the thing that makes focus
legitimate.** The HCI antidote to mode error is two-part (visible *and* cheap to exit), and only the
first part was specified above. Worse: without a good exit, slice 3 (tool narrowing) degrades from an
affordance back into the fence that was deleted. So exit deserves its own design.

### The reframe: exit changes a default, it does not lift a restriction

Because the ask always wins, focus never actually *blocks* anything. So "exit the focus" does not
mean "regain access" — it means **stop biasing the defaults**. That single sentence resolves most of
the design questions, because it means exiting is always safe, never urgent, and never destructive.

It also means the system should never *force* an exit to get work done. If the author, mid
`draft-scene`, asks about the ending — that turn is simply answered. Focus is a default, and
defaults don't need to be dismissed to be overridden.

### There is no single "clear" — there are five exits

Conflating them is the bug. Each wants different UI and different state handling.

| exit | trigger | what happens to state |
|---|---|---|
| **Complete** | the `done()` predicate fires | auto-clears; UI shows "✓ interview complete → next: logline"; derived stage takes over |
| **Abandon** | author clicks ✕ | back to `wide`; subject tray **survives** (it's independently useful); journal the abandonment |
| **Switch** | author picks another mode | a transition, not an exit — old focus's `done()` is evaluated and recorded before replacing |
| **One-turn bypass** | author asks something off-focus | **nothing** — the ask wins, focus persists. This is the common case and must not thrash the mode |
| **Drift** | N consecutive off-focus asks | *suggest* a switch as a chip. Never auto-switch |

The fourth row is the one most designs get wrong. A focus that clears itself the moment you ask one
tangential question is worse than no focus at all — you'd spend the session re-setting it. **A single
off-focus ask is not evidence of a mode change; a pattern of them is.**

### Three actors can exit — and the agent must be one of them

- **The author** — a ✕ on the chip, or plain language ("forget scene 14", "let's step back"). The
  typed exit matters more than the chip here: this is a chat product, and the author will *say* it
  before they click it. So the agent needs to recognize the intent and act on it.
- **The system** — the `done()` predicate. Self-clearing, per §4.
- **The agent** — this is the important addition. It must be able to *request* a focus change:
  `propose_focus_change(mode, why)`, or the existing `ask_author` path.

That third actor is what converts tool narrowing from a fence into an affordance. Consider slice 3
without it: the agent is in `draft-scene`, realizes the scene can't be written until a thread is
fixed two acts back, and finds the expansion tool absent from its belt. With no way to say so, a
capable model does the worst possible thing — it **improvises a workaround** (hand-writes what it
should have generated, or silently narrows the task) rather than reporting the obstruction. Every
narrowing needs a "this isn't the right focus for what you're asking — want to switch?" path, and
the system prompt must name it.

> **Invariant: a narrowing that the agent cannot name and cannot escape is a fence, regardless of
> what the design doc calls it.**

Note this preserves *AI proposes, author owns*: the agent requests, the author confirms. The agent
never silently re-scopes itself.

### Resume: confirm, never silently restore

The highest-risk moment for a mode error is **returning after a gap**. The author comes back
tomorrow; the run row still says `draft-scene: scene 14`.

- If `done()` is now true → it already self-cleared. Show what completed.
- If `done()` is still false → **do not silently resume.** Show it as a resumable chip: *"Still
  drafting scene 14 — continue, or clear?"*

Silent restore is exactly how invisible modes are born again. A focus older than the session should
have to re-earn its authority, and `setAt` on the row is already there to detect it.

### Exit must not depend on the agent's cooperation

Two mechanical rules:

1. **Clearing is a plain row write, never a tool call.** The author must be able to clear focus while
   a turn is mid-flight, while the agent is stuck, or while it's in a retry loop. Anything that
   routes exit *through* the agent inherits the agent's failure modes.
2. **Focus is read at turn start**, exactly like `bookState`. A mid-turn clear takes effect on the
   next link rather than corrupting the running one — deterministic, and the same discipline the run
   row already uses for cooperative cancel.

### The caching physics decide the UX

Where the focus declaration *lives* determines what switching costs — and this is not a detail:

| what focus controls | where it lives | cost of a switch |
|---|---|---|
| ambient blocks, skill briefs, subject hydration (slices 1–2) | volatile tail, inside `<book_state>` | **≈ free** — already the uncached region |
| a mode addendum in the system prompt (like `autoLine` / `effortLine`) | position 0 | busts the cached prefix |
| **the tool belt** (slice 3) | front of the cacheable prefix on Anthropic-shaped caching | **busts everything** — full re-prefill |

So the physics agree with the UX instinct: **slices 1–2 make switching cheap enough to be casual;
slice 3 makes it expensive enough that it must be deliberate.** That is a real argument for
chip-click-or-confirmed-proposal switching and *against* automatic drift-based switching — and an
argument for keeping the mode's *instruction text* in the volatile tail even after slice 3, so only
the belt itself sits in the expensive region. Worth measuring at build time via `ai_calls`
(cache-read vs input tokens) rather than assumed, since the active tier is OpenRouter/DeepSeek and
caching behaviour is provider-specific.

### Minimal viable exit

For slice 1, this is genuinely small:

1. ✕ on the chip → `wide`. Always visible, always enabled, one click.
2. `done()` fires → auto-clear with a visible completion transition.
3. Plain-language exit recognized by the agent → it proposes the change, author confirms.
4. Returning to a stale focus → confirm, don't restore.

Drift detection and `propose_focus_change` can wait for slice 3, which is when they start being
load-bearing.

---

## 7. Verdict

**Yes — build it, in that order.** Not because the agent needs a new capability, but because it
already *has* a mode and currently hides it from the one participant who could correct it.

The proposal is roughly **80% anchoring** (ambient scoping, skill selection, opening framing,
completion predicates), **20% affordance narrowing** (the tool menu) — which is defensible as long
as it stays legible and escapable — and **0% of the thing that was deleted**, provided the
visibility and write axes are written down as invariants now rather than defended by memory later.

The single best idea in it is the one that was not framed as the point: **a focus that knows when it
is done.** That is what separates this from every modal UI that ages badly.

And the hard requirement, per §6a: **exit is not a feature of focus, it is the condition on which
focus is allowed to exist.** A narrowing the agent cannot name and the author cannot clear in one
click is a fence wearing a different word.

## Vocabulary

*mode error* (acting under a wrong mode belief — the core risk of any modal interface; antidotes are
visibility + cheap exit) · *implicit vs explicit state machine* · *affordance vs permission* (what is
offered vs what is allowed) · *capability boundary vs scope boundary* · *salience / attention budget*
· *completion predicate* (a mode that computes its own exit) · *policy-as-data* · *derived proposes,
user disposes* · *escape-hatch legibility* (a narrowing must announce its own way out) · *the
reachability test* (curation is anchoring iff the omitted thing is still reachable).
