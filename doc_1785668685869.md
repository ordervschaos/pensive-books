# Where the DNA agent stands against 2026 agent-building standards

**Verdict: the substrate is ahead of the field; the feedback loop is behind it.**

You have built an unusually good *world model* for an agent — a typed, durable, user-visible
external state (the DNA tree), staged writes, a verify layer, policy-as-data. Most teams bolt
"structured note-taking" onto a chat agent as an afterthought; here the note **is** the product.

You have built an unusually thin *learning loop* — no trajectory evals, no cross-run learning, and
most of the app's diagnostic power isn't wired into the agent's tool belt. The agent can act on the
book far better than it can *perceive* the book, and it never gets better at your books over time.

---

## 1. The standard, as of mid-2026

Twelve dimensions recur across Anthropic's context-engineering guidance, the harness-engineering
catalogue, and the agent-eval literature:

| # | Dimension | What "good" looks like now |
|---|---|---|
| 1 | Agent loop | ReAct with turn budgets, loop detection, durable/resumable execution |
| 2 | Context engineering | JIT retrieval, progressive disclosure, compaction, prompt caching, context-rot awareness |
| 3 | Tool design | Small non-overlapping set (~12–20), token-efficient returns, schema as the constraint |
| 4 | External state | Filesystem-as-context; agent writes notes *outside* the window and re-reads them |
| 5 | Verification | Generator–critic loop; deterministic checks + LLM-as-judge hybrid; verify-then-commit |
| 6 | Human-in-the-loop | Approval flows, tool-risk ratings, defense-in-depth |
| 7 | Planning | Plan-and-execute; **state-machine guardrails** that shrink the tool space per phase |
| 8 | Subagents | Isolated context windows returning 1–2k-token condensed summaries |
| 9 | Memory / learning | Reflect over past trajectories → distilled skills / improved prompts (GEPA, Letta) |
| 10 | Evals | Three levels: end-to-end, **trajectory**, component. Calibrated judges |
| 11 | Observability | Full call tracing, cost/latency/tool-frequency metrics |
| 12 | Cost discipline | Cache-hit rate as a first-class production metric |

Two claims worth internalising:

- **Context rot.** Recall degrades as a *gradient*, not a cliff, as the window fills. Context is a
  finite resource with diminishing marginal returns — the goal is "the smallest set of high-signal
  tokens," not the largest.
- **Tool space is a lever.** One reported result: local models went from 2/10 to 10/10 on a task
  subset *purely by shrinking the available tool set*. Fewer choices at each phase = better choices.

## 2. The scorecard

### 🟢 At or above standard

**External state as the substrate (#4) — your strongest asset.**
`book_nodes` is a typed tree that is simultaneously the agent's working memory, the user's editing
surface, and the artifact being produced. Anthropic's "structured note-taking" pattern and the
"filesystem-as-primary-interface" pattern both point at this; you have the stronger version, because
the note is *schema-validated* and *the deliverable*, not a scratchpad.

**Staged writes / human-in-the-loop (#6).**
The agent has **no** write path to `book_nodes`. Every mutation is a `propose_*` command object the
user (or auto-accept) applies. This is the **command pattern** used as a safety boundary — capability
removal, not permission checking. Stronger than the tool-risk-rating schemes in the catalogue.

**Schema-as-constraint (#3).**
`dnaSchema.ts` + fail-closed `validateOps` means bad structure is rejected at the boundary with
feedback, not caught by a runtime guard downstream. The catalogue calls this
*schema-filtered planning* — enforce behaviour via tool schema rather than runtime checks.

**Context hygiene mechanics (#2) — more sophisticated than most.**
`supabase/functions/book-agent/transcript.ts` alone implements four named patterns:
- `compactTranscript` — prunes stale bulky reads once the transcript grows (context compaction)
- `withCacheBreakpoints` — ephemeral cache marks on a stable prefix (prompt caching; Manus calls
  cache-hit-rate the single most important production metric)
- `withBookState` — book state attached **only** to the latest turn, so the model cannot ground on a
  stale tree. This is a genuinely good move and doesn't have a common name; call it *state recency
  pinning*. It's the fix for the classic agent failure of reasoning over an outdated snapshot.
- `FORCE_COMMIT_AFTER_READS = 15` + `trailingReadRun` — **loop detection middleware**: catch a
  read-spiral and force a commit before it eats the budget.

**Durable agent loop (#1).**
`advance.ts` — `MAX_TURNS`/`AUTO_MAX_TURNS` runaway guards, plus a wall-clock-aware driver that runs
turns back-to-back in one worker and self-chains a fresh worker at the ~150s Supabase boundary. That
is **durable execution** over a platform limit, not a retry hack.

**Verification layer (#5).**
`plan-gate`, `mandate-gate`, structural lints, vertical-fit lints, `verify.ts` auto-injection in auto
mode. The recommended shape is exactly the hybrid you have: *deterministic checks for exact things
(lints), LLM-as-judge for anything that depends on output quality (gates)*.

**Tool count (#3).** 14 tools. Claude Code sits at ~12, Manus under 20. You are in the band.

**JIT retrieval (#2).** `read_node` / `search_nodes` / `get_schema` instead of dumping the tree —
lightweight identifiers, load on demand. Textbook progressive disclosure.

**Observability (#11).** Every Claude call flows through one `_shared/claude.ts` chokepoint into
`ai_calls`, with `provider` recorded. Most teams do not have this.

**Policy-as-data.** Structure templates (Weiland 3-act), lint configs, genre presets — a new method
is one registry entry. Not on the standard lists, but it's the *declarative workflow* family and it's
a real strength.

### 🟡 Present but partial

**Planning / state-machine guardrails (#7).**
`dna-journey.ts` computes the current rung and injects it as advisory context — "anchor, not fence."
That's a deliberate, defensible product choice. But it means **all 14 tools are live at every stage**.
The standard now says: constrain the tool space *per phase*. At the premise rung, `propose_prose_render`
is noise. This is the cheapest available quality win.

**Subagents (#8).**
You have sub-*calls* (`audit_vision`, the gates) but not subagent *isolation with condensed returns*.
A sub-call shares the parent's framing; a subagent burns its own window and hands back 1–2k tokens.
The verify reads are the natural subagent fleet and they aren't wired.

**Compaction (#2).**
You prune stale reads but never summarize-and-restart. Long threads still rot; the mitigation is
social (start a new chat) rather than automatic.

### 🔴 Below standard

**Trajectory evals (#10) — the single biggest gap.**
The standard is three levels:
1. *End-to-end* — did the task succeed? → you have this, **manually**: the editor's read.
2. *Trajectory* — was the path sound? Tool choice, redundant reads, wasted turns, recovery.
   → **you have nothing here.**
3. *Component* — which piece broke? → `ai_call_evals`, on-demand, per-call.

Nothing regression-tests the agent. A prompt change today is validated by vibes. Note that PM Now #1
("re-exercise the live full-book build," record read-round-trip counts per turn) is *precisely the
hand-run version of a trajectory eval* — which is the argument for making it a harness instead of a
ritual.

**Cross-run learning (#9).**
`craft_overrides` is per-book and *author*-authored. There is no reflect-over-trajectories loop, no
distilled skills, no failure→prompt-improvement path. The agent starts every book equally naive and
never gets better at *your* books. The 2026 framing is "continual learning in token space" — update
the context, not the weights — and you have the storage for it (`book_agent_sessions`, `ai_calls`)
but no loop over it.

**Diagnostics not in the tool belt — the sensing asymmetry.**
`read-confusion`, `read-facts`, `read-shape`, `read-synopsis`, `read-logline`, `read-premise`,
`read-meters`, structure-miner: all real, all wired to UI panels, **none callable by the agent**. Its
only sense organ is `check_against_contract`.

> The app can compute more about whether the book is good than the agent can perceive.

This is the same point `docs/true-agent.md` makes as *generate↔verify duality*: an agent with taste
needs to *read what it wrote* and compare observed against planned. Right now the reading happens,
but in a different room.

## 3. The picture

```
                 ┌─────────────────────────────────┐
                 │          DNA AGENT              │
                 │  14 tools · journey ladder      │
                 └───────┬─────────────────▲───────┘
      propose_* (staged) │                 │  read_node / search_nodes  ✅ JIT
                         ▼                 │
                 ┌─────────────────────────┴───────┐
   user accept → │      DNA TREE (book_nodes)      │ ✅ external state = the artifact
                 └───────┬─────────────────────────┘
                         │ render
                         ▼
                 ┌─────────────────────────────────┐
                 │     PROSE (digest + brief)      │
                 └───────┬─────────────────────────┘
                         │
      ╭──────────────────┴──────────────────╮
      │  VERIFY LAYER                       │
      │  lints ✅  gates ✅   ← wired       │
      │  cold-read, facts, shape, meters,   │
      │  structure-miner  ← 🔴 UI ONLY      │
      ╰──────────────────┬──────────────────╯
                         ┊
                         ┊  🔴 MISSING: nothing flows back
                         ┊     to make the agent better
                         ✕
```

Two arrows are the whole story: the **verify → agent** arrow is thin (only lints and gates make it
back), and the **outcome → agent** arrow does not exist at all.

## 4. What I'd do, in order

1. **Wire the reads into the tool belt.** `read_confusion`, `read_facts`, `read_shape` as agent tools.
   Highest value-to-effort in the whole list: the machinery exists, it just isn't reachable. Turns a
   blind writer into one that can read its own work. *(closes the sensing asymmetry)*
2. **Phase-scope the tool space.** Filter the tool array by journey rung. Keep the ladder advisory for
   *conversation*, but make it binding for *tool availability*. Cheap, mechanical, evidence-backed.
3. **Make Now #1 a harness, not a ritual.** Codify the full-book build as a repeatable trajectory eval
   with recorded metrics (turns, read-round-trips, cache-read ratio, cost, lint pass-rate). You are
   already going to run it by hand — the marginal cost of scripting it is small and it becomes the
   regression test you don't have.

   > **Ritual vs. harness — the distinction in full.**
   >
   > A **ritual** is a procedure a *person* performs: sit down, run a live "build all," watch it,
   > eyeball `ai_calls`. That is what Now #1 currently specifies. It yields a verdict at one point in
   > time, held in your head and a WORKLOG line.
   >
   > The problem isn't that it's manual — it's that **the result isn't comparable**. Change the agent
   > prompt next week and there is no baseline to diff against; you'd have to redo the whole ritual to
   > know whether you improved anything. Because that's expensive, you won't. Quality then drifts
   > unmeasured.
   >
   > A **harness** is the same run, *instrumented*: a script that drives the build on a fixture book and
   > writes per-run metrics to a file — turns used, tool-call histogram, read-round-trips per turn,
   > cache-read/input ratio, cost, wall-clock, lint pass-rate, gate verdicts. Every future change is then
   > **compared, not felt**. That is the move from a one-off check to a *regression test with a baseline*
   > — in eval vocabulary, converting a manual **end-to-end** check into an automated **trajectory** eval
   > (§2, the level you're missing).
   >
   > The economics are what carry it: **the build run is already being paid for.** The marginal cost is
   > the *recording*, not the *running*. And step 5 is strictly blocked on this — you cannot reflect over
   > trajectories you never wrote down.
   >
   > *Caveat, so this doesn't get over-built:* "harness" here means **instrument the run you're already
   > doing**, not "stand up a nightly CI job." A full-book build is expensive (baseline: ~$0.33 for an
   > editor's read alone) and fixture books drift. Start by recording to a file; automate the cadence
   > later, if ever. `scripts/` already has this exact shape — `dna-flow-test.mjs`,
   > `prose-context-experiment.mjs`, `model-prose-compare.mjs` — this is that pattern pointed at the
   > agent loop instead of at prose or models.
4. **Subagent the expensive reads.** Isolated window, condensed return. Keeps the main thread clean.
5. **Then, and only then, cross-run learning.** Reflect over `ai_calls` + sessions to distil recurring
   failures into craft-KB entries. This one needs (3) first — you cannot learn from trajectories you
   do not measure.

Note the dependency: **1 and 2 are cheap and independent; 5 is blocked on 3.** The ordering isn't
preference, it's the graph.

## 5. Where the eval harness actually gets built

**Build the scorer, not the driver.** They are separable halves and only one is cheap.

### The driver is the expensive half — don't start there

The autonomous build loop is **split-brain**: the edge fn proposes one change and idles; the client
(`useAutoAccept`) applies it and calls `continueAgent`; repeat. The apply engine is *deliberately*
client-side — `apps/web/src/features/dna/hooks/useAutoAccept.ts:5-6`:

> "…with the write logic staying client-side (no server-side duplication of the engine)."

So a headless Node driver would need its own copy of `applyAgentProposal` — a **third twin** of logic
already parity-locked in two places. That is the trap.

This also explains why the existing scripts don't already answer Now #1: `dna-flow-test.mjs` and
`dna-short-story.mjs` sidestep the agent entirely by calling `runDnaExpand` through `eval-bridge.mjs`.
They measure the **generation ladder**, not the **agent trajectory** — and they run against a mirror
that is explicitly, by standing decision, *not* kept in sync with the edge functions.

### The scorer is nearly free — everything is already logged

`ai_calls` already carries a complete trajectory record: `input_tokens`, `output_tokens`,
`cache_read_tokens`, `cache_write_tokens`, `latency_ms`, `stop_reason`, `error`, `status`, `fn`,
`model`, `provider`, `operation`, `node_id`, `transcript_index`, `artifacts` — plus
`book_agent_runs.steps` for the tool sequence.

You do not need to *drive* a run to *score* one; you need to **read** one. And the run it scores is
the one you were going to do by hand regardless. **Now #1 stops being a ritual the moment its output
is a metrics file instead of an impression** — with no change to how the run is triggered.

```
scripts/agent-trajectory-eval.mjs      # read-only: book_id | run_id → metrics.json + report.md
scripts/lib/trajectory-metrics.mjs     # pure derivation (sits beside prose-lints.mjs)
scripts/.agent-trajectory/<run>.json   # baselines — gitignored, like the other .dna-* artifacts
```

Metrics worth emitting:

| Metric | Source | Why |
|---|---|---|
| turns used vs. ceiling | `book_agent_runs.turns` | headroom / runaway proximity |
| tool-call histogram | `steps` / `output_json` | which tools actually earn their slot |
| **read-round-trips per turn** | `steps` | the existing Now #1 bar |
| cache-read ÷ input ratio | `cache_read_tokens` / `input_tokens` | the existing Now #1 bar |
| cost by provider | tokens × rate, `provider` | cost-per-book attribution |
| wall-clock / latency spread | `latency_ms` | worker-ceiling proximity |
| error + retry count | `error`, `status` | recovery behaviour |
| force-commit trips | `steps` | how often the read-spiral guard fires |
| post-run tree health | `dnaHealth` + lints | outcome, not just path |

### The separation worth naming

This is **observer vs. actuator**. The observer is read-only, commits to no architecture, and pays off
immediately. The actuator forces a decision about where the apply loop lives. Build the observer first
and you get the baseline without buying that decision.

When the driver *does* become worth it, build it as a **server-side drive endpoint**, not a Node
script — because "apply + continue with no browser tab open" is not a test fixture, it is a missing
**product** capability (autonomous build currently requires a tab to stay open). Ship that and the
harness collapses to a one-line POST for free.
