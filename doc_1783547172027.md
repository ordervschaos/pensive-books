## Part 2 — What "§v1/§v4" meant, and why it was the top Now-slot candidate

### Where this sits
This lives in the **verify layer** — the part of the DNA pipeline that reads a generated book
*back* and checks whether it's actually good, as opposed to the **generation layer** that writes
it in the first place. Specifically it's about the **agent loop**: the AgentRail agent running in
"auto" mode, generating a whole book hands-free by looping propose → apply → verify → repeat.

### In plain words
On 2026-07-08, someone actually pointed the auto-mode agent at a live book and said "build the
whole thing, don't stop." That single test — a **live-run exercise** — surfaced four concrete bugs,
labeled §v1 through §v4 in `docs/agent-improvement-remaining.md`. Two are fixed. Two are open:

- **§v1 — the verify judge over-scopes threads.** After the agent writes a scene, a separate
  "judge" pass checks it against the plan (a **verify** step, structurally the same idea as a CI
  test that runs after a commit). This judge is currently too trigger-happy: it flags things as
  broken that aren't, which is **alarm fatigue** — too many false alarms and you stop trusting or
  acting on any of them.
- **§v4 — worker-limit errors strand renders.** Prose generation on the DNA path is a stream:
  browser opens a connection to a Supabase edge worker, the worker calls the model, and text
  streams back token by token (this is the ["prose streaming
  proxy"](project_prose_streaming_proxy) pattern already in your memory — it exists specifically
  to dodge Supabase's ~150s function timeout). Under concurrent load, the worker sometimes returns
  a `546 WORKER_RESOURCE_LIMIT` error mid-stream. When that happens, the prose that *did* stream
  back never gets written to the database, and the `ai_calls` log row for that call gets stuck
  in `running` forever instead of failing cleanly — a **stranded state**: the system doesn't know
  the operation died, so nothing retries or cleans it up.

### Why it matters
This is the actual bottleneck for **M1** (your milestone: one self-generated book the builder
reads end-to-end with no edit-reflex). The live-run notes say it directly: *"a hands-free 'build
all' needs [these] fixed at minimum... closing the driving tab silently freezes the build."*
Everything else on the roadmap — Structure Miner, Brief→Mandate, obligation ledger — improves the
*quality* of a generated book. §v1/§v4 are about whether the book can even get **built** without a
human babysitting every step. Different axis, and currently the limiting one.

### The system, roughly
```
   author clicks "auto" ──▶ AgentRail agent loop (client-driven, runs in an open browser tab)
                                   │
                    propose (ops) │  apply (write to book_nodes)  │  verify (judge pass)
                                   ▼                                ▼
                         ┌─────────────────┐            ┌────────────────────┐
                         │  dna-expand fn   │──stream──▶ │  §v4: worker dies   │
                         │ (prose/beat gen) │            │  mid-stream (546)   │
                         └─────────────────┘            │  → prose lost,      │
                                                          │  ai_calls stuck     │
                                                          └────────────────────┘
                                   │
                                   ▼
                         ┌─────────────────┐
                         │  verify judge    │──▶ §v1: over-flags threads
                         │ (P2.3 loop)      │    → false alarms, agent
                         └─────────────────┘      or author stop trusting it
```
Stakeholders: you (the only end user right now, per STATE.md — "primary user is the builder until
M1"); the agent itself, which needs the verify signal to be trustworthy to act on autonomously;
and the Supabase worker pool, a shared resource that both `dna-decompose` (EPUB import) and
`dna-expand` (generation) compete for — which is *why* §v4 happens under concurrent load.

### Reference
The concrete stuck rows are named in the doc: `ai_calls` rows 7347 and 7352 stayed `running`
after a 546 error during a real build attempt on book 1229's scene 9. That's not hypothetical —
it's a specific, reproduced incident, which is why it's rated as fixable/open rather than
theoretical.

### The recommendation, restated
Since Brief→Mandate turned out to already be shipped, it drops out of the ranking entirely. Of
what's left in `Next`, Obligation ledger completion is the strongest M1 case (unresolved plot
threads at the end of a book are exactly the kind of thing that triggers edit-reflex on a full
read-through) — but nothing beats finishing §v1/§v4 first, since until "build the whole book"
survives, there's no complete self-generated book to even test read-through depth against.
